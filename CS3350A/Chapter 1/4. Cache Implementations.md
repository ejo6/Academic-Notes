## Overview

This note covers **how a cache is actually built and managed**: how memory addresses map onto cache locations, how a cache decides whether it holds a piece of data, what happens on hits and misses (reads and writes), and how design choices (size, block size, associativity, write policy) trade off against each other.

The big picture in one sentence: a cache is a small, fast, hash-table-like structure sitting in front of a bigger, slower memory. Everything below is about the details of that hash table.

### Who manages each level of the hierarchy?

Recall the hierarchy: CPU ← Registers ← L1 ← ... ← Main Memory ← Disk

|Boundary|Managed by|
|---|---|
|Registers ↔ Cache|The **compiler** (sometimes with help from the programmer) decides which values live in which registers|
|Cache ↔ Main memory|The **cache controller** (hardware) moves blocks automatically|
|Main memory ↔ Disk|The **operating system** (virtual memory), the **TLB** (hardware that speeds up virtual → physical address translation), and the programmer (organizing data into files)|

The key takeaway: as a programmer you do **not** explicitly move data between cache and memory. The hardware does it invisibly, which is why you must understand its behaviour to write cache-friendly code.

### The four cache design questions

1. How best to organize the memory blocks (a.k.a. **lines**) inside the cache?
2. To which line of the cache does a given main-memory address map? (Since the cache is a subset of memory, many addresses share the same cache location.)
3. How do we know if a block of main memory currently has a copy in the cache?
4. How do we quickly find that copy?

Sections 2 and 3 answer these. Questions 3 and 4 are answered by the **valid bit** and the **tag**.

### Key terms (from earlier lectures, needed throughout)

- **Hit**: the requested data is in the cache. **Miss**: it is not.
- **Hit rate** $=$ hits / accesses, **miss rate** $= 1 -$ hit rate.
- **Miss penalty**: extra time to fetch the block from the next level down.
- **Temporal locality**: recently used data is likely to be used again soon.
- **Spatial locality**: data near recently used data is likely to be used soon (this is why we fetch whole blocks, not single bytes).

## General Organization of a Cache

A cache is a 2D array:

- The cache has $R = 2^s$ **sets**.
- Each set holds $N \geq 1$ **lines** (also called _ways_ or _blocks_).
- Each line holds $B = 2^b$ bytes of data, plus **metadata**: 1 **valid bit** and $t$ **tag bits**.

![[Screenshot 2026-09-21 at 1.59.00 PM.png|489]]

The data capacity of the cache (metadata not counted) is: $$ C = B \times N \times R $$ All of $B$, $N$, $R$ are powers of 2.

Think of it as a hash table: the **set index** is the hash code (it picks the bucket), and the **tag** is the hash key (it identifies which memory block is currently sitting in the bucket). Since many memory blocks hash to the same set, the tag is needed to tell them apart.

### What the metadata means

- **Valid bit**: is there real data in this line? All lines start invalid (the cache is empty at power-on). A tag match is meaningless if the valid bit is 0.
- **Tag**: the upper address bits that identify _which_ memory block is stored in this line.
- **Data block**: the $B$ bytes copied from memory.

Storage overhead is real: a cache with $C$ bytes of data needs _more_ than $C$ bytes of SRAM once valid and tag bits are counted. Larger blocks amortize this overhead (see the worked example below).

## Memory-Cache Mapping (Addressing)

### Splitting the address

An $m$-bit address $A$ is split into three fields, from most to least significant:

|Field|Width|Purpose|
|---|---|---|
|Tag|$t$ bits|Compared against the stored tag(s) to detect a hit|
|Set index|$s$ bits|Selects which set to look in|
|Block offset|$b$ bits|Selects the starting byte within the block|

The field sizes follow directly from the cache parameters: $$ b = \log_2(B), \quad R = \frac{C}{B \times N}, \quad s = \log_2(R), \quad t = m - s - b $$

### Lookup procedure (hit detection)

1. Use the **set index** to pick a set.
2. In that set, check every line: is its **valid bit** 1 **and** does its stored tag equal the address **tag**?
3. If yes for some line: **hit**. Use the **block offset** to pick out the requested bytes from that line's data.
4. If no line matches: **miss**. Fetch the block from the next level.

The address-to-set mapping can be written as: $$ \text{block address} = \langle\text{tag}\rangle \text{ concatenated with } \langle\text{set index}\rangle, \qquad \text{set number} = (\text{block address}) \bmod R $$ The mod by a power of 2 is free in hardware: it just means "take the low $s$ bits of the block address" (the $s$ bits sitting above the block offset).

> [!note] Coupling The main-memory address space and the cache organization are tightly coupled: the number of address bits $m$ determines how wide the tag must be.

### Word addresses vs. byte addresses

If a machine has $N$-byte words, then **word address** $X$ refers to **byte address** $N \times X$.

Example: on a 16-bit machine (2-byte words), word address 4 is byte address 8 (binary `1000`), not 4 (binary `100`).

**Convention:** unless a problem says otherwise, an address is a **byte address**.

### Why the _middle_ bits for the set index?

Consider a 4-line direct-mapped cache with sets `00, 01, 10, 11`.

- **High-order bit indexing** (use the top bits as the index): adjacent memory blocks all land in the _same_ cache line. Sequential code and array walks would keep evicting each other, so this makes poor use of spatial locality.
- **Middle-order bit indexing** (use the bits just above the offset): consecutive memory blocks map to _different_ cache lines, so the cache can hold up to $C$ bytes of **contiguous** memory at the same time.

This is why the address layout is `tag | index | offset` and not `index | tag | offset`.

## Types of Cache Organization

All three are the same structure with different values of $N$ and $R$.

### Direct-mapped ($N = 1$)

- One line per set. Each memory block can go in **exactly one** cache line.
- $R = C / B$, so the index is large and the tag is small.
- Only **one comparator** is needed. Simple and fast.

### Fully associative ($R = 1$)

- Only one set; a block can go in **any** line.
- $s = 0$, so **no index bits**: the tag is the entire address except the block offset, $t = m - b$.
- $N = C / B$ comparators (every tag must be checked in parallel). Most flexible but most expensive.

### $N$-way set associative

- $N$ is typically 2, 4, 8, or 16.
- A block maps to **one specific set** but can occupy **any of the $N$ ways** within it, giving $N$ placement choices.
- A compromise between the two extremes above.

### Effect of doubling associativity (fixed cache size and block size)

Each doubling of associativity:

- doubles the number of lines per set,
- **halves** the number of sets,
- **decreases** the set index by 1 bit,
- **increases** the tag by 1 bit.

So going toward direct-mapped shrinks the tag and comparator count; going toward fully associative grows the tag until the index disappears.

### Q1 summary: where can an entry be placed?

|Organization|Number of sets|Entries per set|Comparisons per lookup|
|---|---|---|---|
|Direct mapped|number of cache lines|1|1|
|Set associative|(number of lines) / associativity|associativity (typically 2 to 16)|degree of associativity|
|Fully associative|1|number of lines|number of lines|

## Worked Examples: Tracing a Cache

Recipe for any trace problem:

1. Compute $b$, $s$, $t$ from the cache parameters.
2. For each address, write it in binary and split into tag / index / offset.
3. Look at the indexed set: valid and tag match means **hit**; otherwise **miss** and install the block (evicting whatever was there in a direct-mapped cache).
4. Keep a running hit and miss count.

### Example 1: Direct-mapped, $B = 1$

Parameters: $N = 1$, $B = 1$, $R = 4$, so $b = 0$, $s = 2$. Assume $m = 4$, so $t = 2$. Cache starts empty.

Access sequence: 0, 1, 2, 3, 4, 3, 4, 15

|Address|Binary (tag / index)|Result|What happens|
|---|---|---|---|
|0|00 / 00|Miss|Compulsory miss, install in set 0|
|1|00 / 01|Miss|Compulsory miss, set 1|
|2|00 / 10|Miss|Compulsory miss, set 2|
|3|00 / 11|Miss|Compulsory miss, set 3|
|4|01 / 00|Miss|Set 0 holds tag 00 (Mem 0), tag mismatch, so **evict Mem 0**, install Mem 4|
|3|00 / 11|**Hit**|Still there|
|4|01 / 00|**Hit**|Still there|
|15|11 / 11|Miss|Set 3 holds Mem 3, **evict**, install Mem 15|

**Result: 8 requests, 2 hits, 6 misses = 25% hit rate.**

Notice this cache gets **no benefit from spatial locality** because $B = 1$: fetching address 0 did nothing to help address 1.

### Example 2: Direct-mapped, $B = 2$

Parameters: $N = 1$, $B = 2$, $R = 2$, so $b = 1$, $s = 1$, and again $t = 2$ ($m = 4$). Same access sequence.

Each block now holds an aligned pair of addresses: ${0,1}$, ${2,3}$, ${4,5}$, ..., ${14,15}$. The block address is the address with the last bit dropped.

|Address|Binary (tag / index / offset)|Result|What happens|
|---|---|---|---|
|0|00 / 0 / 0|Miss|Loads block ${0,1}$ into set 0|
|1|00 / 0 / 1|**Hit**|Already loaded by the access to 0 (spatial locality)|
|2|00 / 1 / 0|Miss|Loads block ${2,3}$ into set 1|
|3|00 / 1 / 1|**Hit**|Spatial locality again|
|4|01 / 0 / 0|Miss|Set 0 has tag 00, mismatch, evict ${0,1}$, load ${4,5}$|
|3|00 / 1 / 1|**Hit**|Block ${2,3}$ still in set 1|
|4|01 / 0 / 0|**Hit**|Block ${4,5}$ still in set 0|
|15|11 / 1 / 1|Miss|Set 1 tag mismatch, evict ${2,3}$, load ${14,15}$|

**Result: 8 requests, 4 hits, 4 misses = 50% hit rate.** Both examples hold the same 4 bytes of data ($B \times R = 4$), but doubling the block size (and halving the number of sets) doubled the hit rate purely by exploiting spatial locality.

### Circuit-level examples (32-bit addresses, 4 KB of data each)

These slides show the hardware: the index drives a lookup in the array, a comparator checks the stored tag against the address tag, and an AND gate combines that with the valid bit to produce **Hit**.

|Example|Block size|Sets|Byte offset|Block offset|Index|Tag|
|---|---|---|---|---|---|---|
|Direct-mapped 1|4 B (1 word)|$2^{10} = 1024$|2 bits|0 bits|10 bits|20 bits|
|Direct-mapped 2|16 B (4 words)|$2^{8} = 256$|2 bits|2 bits|8 bits|20 bits|
|4-way set assoc.|4 B per way|$2^{8} = 256$|2 bits|0 bits|8 bits|22 bits|

> [!note] Byte offset vs. block offset In word-oriented diagrams the low 2 bits are the **byte offset** (which byte within a 4-byte word) and any bits above that within the block form the **block offset** (which _word_ within the block). Together they make up the $b$ offset bits of the general formulas. In Example 2, $b = 4$: 2 bits select the word (via a 4:1 multiplexer) and 2 bits select the byte.

In the 4-way circuit, the index selects one row in **all four ways at once**. Four comparators check the four tags in parallel; an OR of the four (valid AND match) signals gives **Hit**, and a 4:1 multiplexer picks the data from the matching way.

### Bonus: storage overhead

For Direct-mapped 1 above: each line stores $1 + 20 + 32 = 53$ bits to hold 32 bits of data, so 1024 lines need $1024 \times 53 = 54{,}272$ bits $\approx 6.6$ KB of SRAM for only 4 KB of data (about 66% overhead).

For Direct-mapped 2: each line stores $1 + 20 + 128 = 149$ bits for 128 bits of data, so 256 lines need about 4.7 KB for 4 KB of data (about 16% overhead). **Bigger blocks amortize the tag and valid bit cost.**

### Bonus: computing parameters from a spec

Take a 32 KB, 8-way set-associative cache with 64 B blocks and 32-bit addresses (this matches the Nehalem L1 data cache in the table further down). $$ b = \log_2(64) = 6, \quad R = \frac{32768}{64 \times 8} = 64, \quad s = \log_2(64) = 6, \quad t = 32 - 6 - 6 = 20 $$ Compare the same 32 KB, 64 B-block cache at other associativities:

|Organization|$R$ (sets)|$s$|$t$|
|---|---|---|---|
|Direct-mapped (1-way)|512|9|17|
|8-way|64|6|20|
|Fully associative (512-way)|1|0|26|

Three doublings from 1-way to 8-way, so the tag grows by 3 bits (17 to 20). This confirms the "each doubling adds one tag bit" rule.

## Block Size and Cache Performance

For a fixed cache size, increasing the block size:

- **helps** at first, because more spatial locality is captured (fewer compulsory misses);
- **hurts** once the block becomes a significant fraction of the cache, because a fixed cache size with bigger blocks means **fewer blocks**, so more **capacity misses** and more eviction of useful data;
- also raises the **miss penalty**, since a larger block takes longer to transfer.

The slide's graph shows a U-shaped miss-rate curve for small caches (8 KB, 16 KB): miss rate falls until roughly 64 B blocks and then climbs. Larger caches (64 KB, 256 KB) are flatter, since a big block is still a small fraction of them. Typical block sizes are **16 to 64 bytes** (64 B on modern CPUs).

## Conflict Misses and Thrashing

### Direct-mapped worst case

Direct-mapped, $B = 1$, $R = 4$. Access pattern: 0, 4, 0, 4, 0, 4, ...

Addresses 0 (`0000`) and 4 (`0100`) have the same index `00` but different tags. Each access evicts the other, so **every access is a miss: 8 requests, 8 misses (100% miss rate)**, even though three of the four sets are empty. This is **thrashing**, caused by **conflict misses** (two live addresses fighting for one line).

### The fix: set associativity

Same pattern on a **2-way** cache with $B = 1$, $R = 2$ (2 sets of 2 ways, 4 bytes of data in total, the same capacity as the direct-mapped cache above).

With $R = 2$ the index is 1 bit and the tag is 3 bits. Both addresses map to set 0 (index bit 0), with tags `000` and `010`. The first two accesses are compulsory misses; after that both blocks sit side by side in the two ways of set 0, so **every remaining access hits: 8 requests, 2 misses = 75% hit rate**.

### Benefits of associativity in general

- The biggest gain is going from **direct-mapped to 2-way** (over a 20% reduction in miss rate in the slide's data).
- Returns diminish quickly beyond 4-way or 8-way, especially for large caches.
- The choice depends on **cost of a miss vs. cost of the implementation**.

## Replacement Policies and the Cost of Associativity

### Which way do we evict on a miss?

- **Direct-mapped:** no choice, only one line.
- **Set/fully associative:** pick a victim among the ways.
    - **Random**: cheap, surprisingly decent.
    - **LRU (Least Recently Used)**: evict the line unused for the longest time. Exploits temporal locality. The hardware must track relative recency of all ways in the set.
        - For **2-way**, LRU needs just **1 bit per set**: set it on a reference to one way (and clear the other's).
        - LRU gets expensive above 4-way, so real caches often use **approximate LRU** ("$\sim$LRU" in the processor table).
    - **FIFO (First In First Out)**: evict the oldest _loaded_ line. Easy to implement with a circular buffer or counter.

### Hardware costs of an $N$-way cache

- $N$ **comparators** (area and delay on the chip) to check all the tags in parallel. (The slide ties this to LRU, but the comparators are fundamentally needed for tag matching; LRU adds further tracking logic.)
- A **multiplexer delay** to select the matching way before data is available.
- In a direct-mapped cache the data block can be read out **before** the hit/miss decision is finished, so the processor can optimistically use it and recover later if it was a miss. That trick is **impossible** for set-associative caches, since you do not know _which_ way's data to use until the tag compare finishes.

## Handling Cache Hits and Misses

### Read hits (instructions and data)

The best case. Do nothing special; return the data.

### Write hits (data only)

The cache copy is modified, but what about the copy in memory? Two policies:

**Write-through**

- On every write, update both the cache **and** the next level down. The two are always consistent.
- Naively slow, because write speed is limited by the lower level.
- Fix: put a **write buffer** between levels; the processor continues and stalls only when the buffer fills up.

**Write-back**

- Update **only the cache** and mark the line **dirty** (needs an extra _dirty bit_ per line).
- The next level is updated only when a dirty line is **evicted**.
- Naively needs more than 1 cycle (one to check dirty/evict, one to write), unless a write buffer is used.
- Far less bandwidth to lower levels: repeated writes to the same block cost one memory write in total.

### Read misses (instructions and data)

Stall the processor, fetch the block from the next lower level, **install** it in the cache, forward the requested word to the processor, and let it resume.

### Write misses (data only)

The processor stalls and one of two policies is applied:

**Write allocate**

- Fetch the block from the next level, install it in the cache, then write the updated word into it (install and write can overlap).
- Good if you will probably touch that block again (temporal/spatial locality).

**No-write allocate**

- Do **not** bring the block into the cache; write directly to the lower level (or a write buffer), then resume.
- Good for write-once data (e.g. streaming output).

> [!note] Common pairings **Write-back + write-allocate** is the typical pair (both assume the data will be reused in cache). **Write-through + no-write-allocate** is the other natural pair (both push writes straight down). The processors in the table below use write-back/write-allocate at almost every level.

## The Three Cs of Cache Misses

|Miss type|Cause|How to reduce it|
|---|---|---|
|**Compulsory** (cold)|First reference to a block: cold start, process migration, very first access|Increase **block size** (more data per fetch), but this raises the miss penalty and can raise the miss rate if blocks get too big|
|**Capacity**|The cache is full and cannot hold all blocks the program uses|Increase **cache size** (but access time may grow)|
|**Conflict**|Multiple addresses map to the same set/line although other lines may be free|Increase **associativity**, or increase cache size (more sets means fewer addresses collide)|

Conflict misses only exist in direct-mapped and set-associative caches; a fully associative cache has only compulsory and capacity misses. (In multiprocessors, a fourth type, _coherence_ misses, also appears, but that is beyond this lecture.)

## Improving Cache Performance

Everything is measured with: $$ \text{AMAT} = \text{Time for a Hit} + \text{Miss Rate} \times \text{Miss Penalty} $$ Each optimization attacks one of the three terms.

### (1) Reduce hit time

- Smaller cache, smaller blocks.
- Direct-mapped (no way-select mux).
- For writes: no-write-allocate (just put the write in the write buffer) or write-allocate using a write buffer to avoid the extra cycle.

### (2) Reduce miss rate

- Larger cache; larger blocks (16 to 64 B typical).
- More associativity (more flexible placement).
- A **victim cache**: a small buffer holding the most recently _evicted_ blocks, so a just-evicted block that is needed again is not a full miss.

### (3) Reduce miss penalty

- Smaller blocks (less to transfer).
- Write buffer; on a read miss, check the write buffer (and victim cache) first, since the data might be sitting there "luck".
- **Critical word first**: fetch the requested word first, forward it to the processor, then finish filling the rest of the block.
- **Multiple cache levels** (see below).
- Faster main memory, and better memory **bandwidth** (e.g. wider buses).

### Multi-level caches

- **Reduce miss rate** by growing the cache, which is more feasible as transistors shrink.
- **Reduce miss penalty** by adding levels. History from the slides: L1 has been around for a long time; L2 first appeared on Intel Celeron (1999, 128 KB); L3 appeared in 2003 but was too expensive, and became standard with Intel Nehalem (2008).

**AMAT example** (1 cycle L1 hit, 2% L1 miss rate, 5 cycle L2 hit, 5% L2 miss rate, 100 cycle main memory):

Without an L2: $$ \text{AMAT} = 1 + 0.02 \times 100 = 3 \text{ cycles} $$ With an L2: $$ \text{AMAT} = 1 + 0.02 \times (5 + 0.05 \times 100) = 1 + 0.02 \times 10 = 1.2 \text{ cycles} $$ Adding the L2 cut AMAT from 3 to 1.2 cycles. Note that the L2's 5% is its **local** miss rate: 5% of the accesses _that reach it_ (i.e. that missed L1), not 5% of all accesses. In general: $$ \text{AMAT} = T_{L1} + m_{L1} \times \left( T_{L2} + m_{L2} \times T_{mem} \right) $$

### Example: the set index is recomputed per level

A miss at L1 does **not** reuse L1's set number at L2 — L2 re-splits the *same address* using its **own** $b$, $s$, $t$, and that usually lands on a different set number.

Toy setup, $m = 8$-bit addresses, block size $B = 2$ (so $b = 1$) at both levels, but different capacities: L1 has $R = 4$ sets ($s = 2$), L2 has $R = 8$ sets ($s = 3$).

Take address $107 = \texttt{0110 1011}_2$ (bits numbered 7 down to 0):

|Level|$s$|Index bits used|Index value|Tag bits used|Tag value|
|---|---|---|---|---|---|
|L1|2|bits 2–1 = `01`|1|bits 7–3 = `01101`|13|
|L2|3|bits 3–1 = `101`|5|bits 7–4 = `0110`|6|

Both splits share the same 1-bit offset (bit 0), but because L2 has one more index bit, it grabs an extra bit from what was L1's tag. The result: **L1 looks in set 1, L2 looks in set 5** — for the exact same address. On an L1 miss, the controller doesn't ask "is address 107 in L1's set 1?" again at L2; it asks the question L2's own geometry dictates, which is "is address 107 in L2's set 5?"

(Real Nehalem numbers make the same point: 32 KB 8-way L1 with 64 B blocks gives $s = 6$; 256 KB 8-way L2 with the same 64 B blocks gives $s = 9$ — three more index bits, so L2's set index for a given address is essentially unrelated to L1's.)

### Different goals for L1 vs. L2

|               | L1 (primary)                                              | L2 / L3 (secondary)                                    |
| ------------- | --------------------------------------------------------- | ------------------------------------------------------ |
| Main goal     | Minimize **hit time** (keeps up with the processor clock) | Minimize **miss rate** (to avoid going to main memory) |
| Capacity      | Smaller                                                   | Larger                                                 |
| Block size    | Smaller                                                   | Larger                                                 |
| Associativity | Lower                                                     | Higher                                                 |

Because the L2 catches most L1 misses, the L1 can afford to be small and fast even though that means a higher miss rate. L2 hit time matters less than its miss rate, but it still sets L1's miss penalty. An L3 makes the L2 miss rate slightly less critical. As the slides say: **it's all a balancing act.**

## Real Processors

|                              | Intel Nehalem                                  | AMD Barcelona                                      |
| ---------------------------- | ---------------------------------------------- | -------------------------------------------------- |
| **L1 size and organization** | 32 KB per core; 64 B blocks; split I$ and D$   | 64 KB per core; 64 B blocks; split I$ and D$       |
| **L1 associativity**         | 4-way (I), 8-way (D); $\sim$LRU                | 2-way; LRU                                         |
| **L1 write policy**          | write-back, write-allocate                     | write-back, write-allocate                         |
| **L2 size and organization** | 256 KB per core; 64 B blocks; unified          | 512 KB per core; 64 B blocks; unified              |
| **L2 associativity**         | 8-way; $\sim$LRU                               | 16-way; $\sim$LRU                                  |
| **L2 write policy**          | write-back, write-allocate                     | write-back, write-allocate                         |
| **L3 size and organization** | 8 MB shared by all cores; 64 B blocks; unified | 2 MB shared by all cores; 64 B blocks; unified     |
| **L3 associativity**         | 16-way                                         | 32-way; evict the block shared by the fewest cores |
| **L3 write policy**          | write-back, write-allocate                     | write-back, write-allocate                         |

Observations:

- L1 is **split** into instruction ($I$) and data ($D$) caches so instruction fetch and data access do not conflict; L2 and L3 are **unified**.
- Associativity **rises** as you go down the hierarchy, matching the "L2 focuses on miss rate" principle above.
- All levels here are write-back + write-allocate.

**Older example: Intel Pentium hierarchy.** L1 data cache 16 KB, 4-way, **write-through**, 32 B lines, 1 cycle latency; L1 instruction cache 16 KB, 4-way, 32 B lines; unified L2 of 128 KB to 2 MB, 4-way, **write-back**, write-allocate, 32 B lines; main memory up to 4 GB. Note the write-through L1 backed by a write-back L2: the L2 absorbs the write traffic that the L1 pushes down.

## The Cache Design Space

Several dimensions interact: **cache size, block size, associativity, replacement policy, write-through vs. write-back, write allocation**.

- The best choice is a **compromise**. Each factor helps one thing and hurts another (the slide's U-shaped curve: too little or too much of a factor is both bad).
- The optimum depends on the program's **access characteristics** and on **technology and cost**.
- **Simplicity often wins.**

## Summary and Review

### Critical aspects of the memory hierarchy

- **Principle of locality:** programs access a small part of the address space at any instant (temporal and spatial locality).
- **Three miss types:** compulsory (unavoidable), conflict (add associativity or size; thrashing), capacity (add size).
- **Design space:** total size, block size, associativity and replacement policy; write-hit policy (write-through or write-back); write-miss policy (write-allocate or not); write buffers.

### Three questions to be able to answer

1. **Where can an entry be placed or found?** Cache organization: direct-mapped, set-associative, fully associative (see the Q1 table above).
2. **Which entry should be replaced on a miss?** Easy for direct-mapped (only one choice). Otherwise Random, LRU, or FIFO. LRU is easy and ideal for 2-way; above 4-way its comparison logic is often too costly.
3. **What happens on a write?** Write-through vs. write-back on hits; write-allocate vs. no-write-allocate on misses.

**Typical exam question:** given a list of memory references, describe the cache state after each reference. Use the trace recipe from the Worked Examples section.

### Quick formula sheet

$$ C = B \times N \times R, \quad b = \log_2 B, \quad s = \log_2 R, \quad t = m - s - b $$ Direct-mapped: $N = 1$, $R = C/B$. Fully associative: $R = 1$, $s = 0$, $N = C/B$, $t = m - b$. Set-associative: $R = C/(B \times N)$.
