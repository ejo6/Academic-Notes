## History, Trends, and Basics

### Why memory matters now

CPU performance from a programmer's point of view depends on CPU frequency, the type of instructions performed, and **memory access time**. Recall the CPU-time equation:
$$
\text{CPU Time} = \text{Instruction\_count} * \text{CPI} * \text{clock\_cycle}
$$
Historically the factors of this equation (instruction count, CPI, clock cycle) were controlled by the algorithm, the programming language, the compiler, the ISA, and the processor organization. What that equation hides is that CPI itself is inflated by *stalls* whenever the processor has to wait on memory — this is the gap the rest of the lecture is about.

### The Processor-Memory Gap ("Memory Wall")

Processor speed has historically improved much faster than DRAM (main memory) speed. Plotted on a log scale from 1980-2010, processor performance climbs steeply while memory performance climbs only gradually — the widening gap between the two curves is called the **Processor-Memory Gap**.

The **Memory Wall** is the point at which a program's performance is entirely determined by memory speed rather than CPU speed — i.e., making the processor faster stops helping, because it just spends more time waiting on memory. This is a key motivation for the whole memory hierarchy: without it, fast CPUs would sit idle waiting on slow DRAM.

*Concrete illustration (the copy-matrix example):* two versions of a matrix-copy routine that do the exact same amount of arithmetic and touch the exact same data, differing only in loop order (`i` outer / `j` inner vs. `j` outer / `i` inner):

```c
void copymatrix1(int** src, int** dst, int n) {
    int i,j;
    for (i = 0; i < n; i++)
        for (j = 0; j < n; j++)
            dst[i][j] = src[i][j];
}

void copymatrix2(int** src, int** dst, int n) {
    int i,j;
    for (j = 0; j < n; j++)
        for (i = 0; i < n; i++)
            dst[i][j] = src[i][j];
}
```

Measured: `copymatrix1` took ~0.21s with ~2.07M cache misses; `copymatrix2` took ~0.53s with ~3.98M cache misses — roughly **2.5x slower** despite doing identical work. **Cache misses are the reason for the performance drop.** (This previews *locality*, covered below: `copymatrix1` walks memory row-major, matching how C actually lays out 2D arrays, so it has good spatial locality; `copymatrix2` does not.)

### A historical framing: why we used to not care, and why we do now

In the 1950s-70s, software was mostly mathematical/scientific (the heyday of FORTRAN). Computing resources were extremely limited — as late as the 1980s, a system might have only 64 **mega**bytes of memory. Because of this, algorithm design focused on minimizing the *amount* of memory used: sparse-matrix techniques, symbolic computation, and squeezing numeric types down (`char`/`INT1` = 1 byte, `short`/`INT2` = 2 bytes, `int`/`INT4` = 4 bytes).

Historically, programmers worried about *how much* memory was used because processor speed and memory speed were roughly matched — memory access time was about the same as arithmetic time, so there was no huge latency penalty to hide.

Today the situation has flipped: memory *size* is rarely the limiting factor (laptops with 64 **giga**bytes of RAM; compute clusters with hundreds of GB per processor), so the practical concern shifted from *how much* memory is used to *how* memory is used — i.e., the *access pattern*, because the Memory Wall (memory *speed*) is now the bottleneck. The **memory hierarchy** is the architectural answer to the Memory Wall: a graduated series of storage levels that lets programs mostly interact with something that behaves like it's as fast as the fastest level, while physically getting most of the volume of the cheapest level.

### The memory hierarchy, level by level

The hierarchy (fastest/smallest/most-expensive at top, to slowest/largest/cheapest at bottom):

1. **CPU registers** — inside the processor itself.
2. **CPU cache** — L1, then L2, then L3 (on modern chips, multiple on-chip levels; single-level caches were the norm before roughly the 1990s, when multi-level caching became standard).
3. **Physical memory / main memory (RAM)** — DRAM technologies (EDO, SD-RAM, DDR-SDRAM, RD-RAM, etc.).
4. **Solid-state memory** — SSDs, flash drives (non-volatile).
5. **Virtual memory / secondary storage** — mechanical hard drives, file-based, slow but cheap and huge capacity.

As you go down: speed decreases, cost-per-byte decreases, and capacity increases. As you go up: speed increases, cost-per-byte increases, and capacity shrinks.

A real example (Nehalem, first-generation Intel Core i7): each core has 32KB instruction cache (I$), 32KB data cache (D$), and 512KB L2 cache; all cores share a single 2-24MB L3 cache, plus a memory controller on-die. This is worth internalizing because it shows just how small L1 really is relative to main memory — a few tens of kilobytes vs. gigabytes — which is exactly why *locality* (below) has to hold for caching to work at all.

### Why a hierarchy instead of one big fast memory?

Four enduring hardware/software facts drive this design:
- Fast storage technologies (SRAM) cost more per byte than slow ones (DRAM, disk).
- Fast storage technologies take up more physical die area per byte.
- The gap between CPU speed and main-memory (DRAM) speed keeps widening (the Processor-Memory Gap above).
- The **Principle of Locality** (next section) means most of a program's memory traffic, at any moment, is concentrated on a small chunk of its total data — so you don't actually need all your memory to be fast, only the part currently in use.

Given locality, whole sections of memory can be copied from a lower (slower, bigger) level of the hierarchy up to a higher (faster, smaller) level infrequently, and then the CPU can run for a long stretch referencing only the fast, high-level copy. The net effect: a large pool of memory that costs about as little as the cheapest (bottom) storage, but that *serves* programs at close to the speed of the fastest (top) storage — as long as locality holds.

## The Principle of Locality

> "Programs tend to reuse data and instructions they have recently used." — Hennessy and Patterson, *Computer Architecture*

During any short window of execution, a program is likely to touch only a small portion of its available address space and its available code. This isn't an accident of how people happen to write programs — it's close to unavoidable given how loops, function calls, and arrays are used, and it is precisely what hardware designers count on. If a program's access pattern *doesn't* respect locality, the hardware (the cache) will not serve it well, no matter how well the algorithm is designed in the abstract — this is why "big-O" analysis alone can understate real-world performance differences (as the copymatrix example above showed).

### Temporal vs. spatial locality

- **Temporal locality**: recently accessed items are likely to be accessed again soon. ("If I just touched it, I'll probably touch it again.")
- **Spatial locality**: recently accessed items are likely to have their *neighbors* accessed soon. ("If I just touched address X, I'll probably touch X+1 next.")

*Note:* "items" here can mean data (memory addresses) or instructions.

### Locality in instructions

Instruction locality is less intuitive than data locality since you don't usually think of "the next line of code" as a memory address, but the program itself lives in memory and the PC walks through it just like data pointers walk through arrays.

- **Temporal** locality in instructions comes from: loops (the same few instructions execute repeatedly), and repeated calls to the same method/function.
- **Spatial** locality in instructions comes from: loops, repeated calls to the same method, and the fact that **instruction execution is sequential by default** — with no unconditional jump, the next instruction fetched is the next one in memory, i.e., a neighbor of the current one.

*Caveat:* an inlined function call effectively behaves like an unconditional jump for locality purposes — control moves elsewhere in memory rather than falling through — even though nothing in the source code looks like a "jump."

*Important distinction the slides emphasize:* continually executing the same *type* of instruction (e.g., always doing additions) is **not** locality. Locality requires the exact same instruction, at the exact same memory address, after compilation — same opcode *and* same operands, not just the same category of operation.

### Locality in data

Easier to build intuition for than instruction locality:
- Repeated access to the same variable (temporal).
- Sequential access to an array (spatial).
- Initializing a variable right before it's used, rather than up front (keeps the temporal gap short).
- Reusing an already-loaded variable instead of creating (and thus loading/allocating) a new one — every new variable is a fresh entry that must be pulled into cache, so reusing something already resident avoids that cost.

**Prime example — stride-1 access:**
```c
int arr[n];
for (int i = 0; i < n; ++i) {
    printf("%d", arr[i]);
}
```
Walking through an array one element at a time (stride 1) is the canonical example of spatial locality, because consecutive elements sit at consecutive memory addresses.

### Aside: how C (and FORTRAN/MATLAB) actually lay out multi-dimensional arrays

This matters because it tells you which loop order actually gives you stride-1, contiguous access — you can't reason about spatial locality without knowing the underlying layout.

- **C arrays are row-major**: each *row* occupies contiguous memory. `a[i][j]` is equivalent to a single flat index `a[i * ncols + j]`.
  $$
  \begin{bmatrix} 0 & 1 & 2 \\ 3 & 4 & 5 \\ 6 & 7 & 8 \end{bmatrix} \implies [0,1,2,3,4,5,6,7,8]
  $$
- **FORTRAN and MATLAB are column-major**: each *column* occupies contiguous memory.
  $$
  \begin{bmatrix} 1 & 2 & 3 \\ 4 & 5 & 6 \\ 7 & 8 & 9 \end{bmatrix} \implies [1,4,7,2,5,8,3,6,9]
  $$
So in C, the inner loop should iterate over the **last** index (columns, for a 2D array) to get stride-1 access; in FORTRAN/MATLAB it's the opposite.

### Worked locality exercises

**Warm-up:**
```c
int sumArray(int* a, int n) {
    int sum = 0;
    for (i=0; i<n; i++)
        sum += a[i];
    return sum;
}
```
- Stride-1 access to `a` $\implies$ **spatial** locality.
- Temporal locality in the repeated access to `sum`, `i`, and `n` on every iteration.
- *Subtlety:* the temporal locality is in reference to the *pointer* `a` (i.e., the base address/variable itself is reused every iteration to compute an offset), **not** to the array elements pointed at — each `a[i]` is a *different* memory location. Recall `a[i]` is just syntactic sugar for `*(a + i)`.

**Exercise 1** — nested loop, natural (row-major-matching) order:
```c
int sumarray(int[][] a, int M, int N) {
    int i, j, sum = 0;
    for (i = 0; i < M; i++)
        for (j = 0; j < N; j++)
            sum += a[i][j];
    return sum;
}
```
- **Spatial** locality in access to `a` — because the inner loop walks `j` (the last/fastest-varying index), which matches C's row-major layout, giving stride-1 access.
- **Temporal** locality in access to `sum`, `i`, `j`, `N` (all re-read/re-written every inner iteration).

**Exercise 2** — same computation, loops swapped:
```c
int sumarray(int[][] a, int M, int N) {
    int i, j, sum = 0;
    for (j = 0; j < N; j++)
        for (i = 0; i < M; i++)
            sum += a[i][j];
    return sum;
}
```
- **Temporal** locality in `sum`, `i`, `j`, `M`.
- **No spatial** locality in access to `a` — the inner loop now varies `i` (the row index), so consecutive accesses jump by a full row's width (`N` elements) in memory each time, not by 1.
- *Subtlety:* if `M` is *small* (few rows), there's a possibility of *temporal* locality re-emerging in `N` (i.e., if the whole working set is small enough to fit and get reused within cache) — this is a reminder that locality claims often depend on relative sizes (of `M`, `N`, and the cache), not just on the code shape alone. This idea is developed fully in "Advanced Temporal Locality" below.

**Exercise 3** — 3D array, loop order deliberately "wrong":
```c
int sumarray3d(int[][][] a, int N) {
    int i, j, k, sum = 0;
    for (j = 0; j < N; j++)
        for (i = 0; i < N; i++)
            for (k = 0; k < N; k++)
                sum += a[k][i][j];
    return sum;
}
```
This does *not* have good spatial locality as written, because the innermost loop varies `k`, but `k` is the *first* (slowest-varying, outermost) index of `a[k][i][j]` in row-major layout — each step of the innermost loop jumps by a full 2D "slice" ($N \times N$ elements). To fix it via loop permutation so that stride-1 access is achieved, the innermost loop must vary the *last* index (`j`), matching C's row-major convention — e.g., reorder so `k` is outermost, `i` is middle, `j` is innermost:
```c
for (k = 0; k < N; k++)
    for (i = 0; i < N; i++)
        for (j = 0; j < N; j++)
            sum += a[k][i][j];
```

## The Cache Hierarchy

### Structural properties of the hierarchy

Drawn as a pyramid: CPU at the top, then L1$ (4-8 byte "word" granularity), L2$ (8-32 byte "block" granularity), main memory (1-4 blocks at a time), secondary memory (1,024+ byte "disk sector"/"page" granularity) at the bottom. Distance from the processor increases (in *access time*, not necessarily physical distance) as you go down, while the relative *size* of memory at each level increases going down.

**Inclusive** hierarchy: what's in L1$ is a subset of what's in L2$, which is a subset of what's in Main Memory, which is a subset of what's in Secondary Memory. This is what makes "caching" meaningful — a higher level never holds data absent from the level below it; it holds a *copy* of a portion of it.

The CPU looks for requested data first in L1, then L2, and so on down to main memory if needed — modern computers usually have **three levels of cache** before main memory is reached.

### What is a cache, formally?

**Cache**: a small, fast (usually SRAM) storage device that acts as a staging area between the CPU and the larger, slower main memory.

The fundamental recursive idea of a memory hierarchy: for every level $k$, the fast/small device at level $k$ serves as a cache *for* the larger/slower device at level $k+1$. The data held in the cache at level $k$ is always a subset of the data available at level $k+1$ (this is the "inclusive" property above, stated generally for any two adjacent levels, not just L1/L2/MM).

**Why does this work at all?** Two facts combine:
1. Programs access data at level $k$ (the fast level) more often than data at level $k+1$ — this is exactly the Principle of Locality.
2. Storage at level $k+1$ can afford to be slower, bigger, and cheaper per byte, precisely *because* it's accessed less often — you're not paying the full performance cost of using it, most of the time.

Net effect: you get a large pool of memory that costs about as little as the cheap storage near the bottom of the hierarchy, but that serves data to programs at close to the speed of the fastest storage near the top — *provided* locality actually holds for the program in question. This is the payoff of everything covered in the locality section above; it's why locality isn't just a theoretical curiosity but the entire economic justification for building a hierarchy instead of one uniform memory.

### Mechanics of caching: blocks, hits, and misses

Each level of memory is partitioned into fixed-size chunks called **blocks** (all blocks at a given cache level are the same size). The small, fast device at level $k$ caches a *subset* of the blocks from level $k+1$. If block size matches between two adjacent levels, then the "subset of data" is really a "subset of blocks" — data moves between levels in whole block-sized transfer units, never partial blocks.

When the processor requests a memory address contained in some block $b$:
- **Cache hit (at level $k$)**: the program finds $b$ already present in the level-$k$ cache. Fast — no need to go further down.
- **Cache miss (at level $k$)**: $b$ is *not* present at level $k$, so the level-$k$ cache must fetch it from level $k+1$. If the level-$k$ cache is already full, some existing block must be evicted (the "**victim**") to make room for the newly fetched one.

### Cache policies: placement and replacement

Two separate questions arise once a miss occurs and a block needs to be brought in:

- **Placement (mapping) policy** — *where can the new block go?* Each block has one (or more) designated slot(s) it's allowed to occupy in the cache. If all the slots it's eligible for are already full, one of them must be overwritten. Example: a "mod-4 mapping" placement policy sends block $b$ to slot $b \bmod 4$.
- **Replacement policy** — *given that a slot must be freed, which occupant is evicted?* Common policies:
  - **LRU** (Least Recently Used) — evict whichever block hasn't been touched for the longest time. This is a direct application of temporal locality: something not recently used is a good bet to not be needed again soon.
  - **FIFO** (First In, First Out) — evict whichever block has been resident the longest, regardless of recent use.

(Placement and replacement interact — under a direct-mapped placement policy with only one eligible slot per block, there's no actual "choice" left for a replacement policy to make; replacement policy matters more when placement allows a block to go into several possible slots.)

### Three kinds of cache misses

1. **Cold (compulsory) miss** (at level $k$): occurs the very first time a given block $b$ is requested, since it can't possibly already be present. Cold misses are unavoidable — they always occur at least once per block, no matter how good the cache or the access pattern is.
2. **Capacity miss** (at level $k$): occurs because the set of blocks the program is *actively* working with (the "working set") is larger than the level-$k$ cache itself, so not everything currently needed can fit simultaneously — something must be evicted even though it will be needed again soon. This can occur under either a mapping policy or a replacement policy, and is essentially a special case of a conflict miss for when the cache happens to be completely full.
3. **Conflict miss** (at level $k$): a mapping policy restricts each block to a small subset (sometimes exactly one) of possible cache positions. A conflict miss happens when multiple *distinct* level-$(k+1)$ blocks all map to the *same* position at level $k$, so they keep evicting each other even if the cache overall isn't full. Example: under a mod-4 mapping, blocks 13 and 25 both map to index 1 ($13 \bmod 4 = 1$, $25 \bmod 4 = 1$), so requesting one can evict the other.
   - **Thrashing**: a severe, repeated form of conflict miss where two (or more) blocks are locked in a cycle of evicting each other. Example: repeatedly requesting blocks $0, 8, 0, 8, 0, 8, \dots$ under a mod-4 mapping (since $0 \bmod 4 = 8 \bmod 4 = 0$) causes a miss on *every single access*, because each request evicts the block the very next request needs.

### Multi-level caches in practice

A memory access first checks L1; on an L1 miss, it checks L2; on an L2 miss, it goes to main memory (and so on if there are more levels). Data found at any level is passed back up through the levels to the CPU.

*Terminology caveat*: although cache levels are numbered 1, 2, 3, ..., it's common informally to refer to the cache at level $k+1$ as a "**lower**-level cache" *relative to* the cache at level $k$ — "lower" here tracks position further from the CPU (and thus lower in the pyramid diagram), even though the *number* is higher. Don't confuse "lower level" (further from CPU, bigger number) with "lower-numbered level" (closer to CPU, e.g. L1).

### Aside: banked vs. unified caches

- **Banked cache**: a cache split into separate sections for instructions and data (e.g., L1I for instructions, L1D for data). L1 is usually banked. This lets the CPU access an instruction and a piece of data **simultaneously**, since they're in physically separate structures rather than contending for one shared port — this becomes especially relevant later when studying **pipelining**, where fetching the next instruction and accessing data for the current one really do need to happen at the same time.
- **Unified cache**: a single cache where instructions and data are stored together and can be intermixed. (Typically used further down the hierarchy, e.g. L2/L3, where the simultaneous-access benefit of banking matters less and unifying gives more flexible capacity sharing.)

### Cache/memory types and their relative characteristics (reference table)

| "Cache" Type | What's Cached | Where Cached | Latency (cycles) | Managed By |
|---|---|---|---|---|
| Registers | 4/8-byte word | CPU registers | 0.5 | Compiler |
| TLB | Address translations | On-chip TLB | 0.5 | Hardware |
| L1 cache | 32-byte block | On-chip L1 | 1 | Hardware |
| L2 cache | 32-byte block | On/Off-chip L2 | 10 | Hardware |
| Buffer cache | Parts of files | Main memory | 100 | OS |
| Virtual Memory (Paging) | 4-KB page | NVMe/HDD | 100,000 – 1,000,000 | Hardware + OS |
| Network buffer cache | Parts of files | Local disk | 10,000,000 | AFS/NFS client |
| Web cache | Web pages | Remote server disks | 1,000,000,000 | Web proxy server |

Notes worth drawing out:
- The **TLB** (Translation Lookaside Buffer) is itself a cache — specifically an "address-translation cache" that caches virtual-to-physical memory address mappings, so that address translation (needed for virtual memory) doesn't have to be redone from scratch on every single memory access.
- **AFS** (Andrew File System) and **NFS** (Network File System) are examples of *distributed* file system protocols — relevant to why a "network buffer cache" entry even exists in this table (caching parts of files that live on a remote machine).
- Notice the *massive* jump in latency once you leave on-chip caches: registers/TLB/L1/L2 are all under 10 cycles, but paging out to disk is 100,000-1,000,000 cycles, and a network round-trip for a web cache miss is roughly a *billion* cycles. This is the Memory Wall made concrete in units the CPI-stall formula (next section) will use directly.

## Cache and Memory Performance

### Extending the CPU-time equation to account for memory

The simplified CPU-time model (Instruction\_count × CPI × clock\_cycle) implicitly assumed a fixed, "ideal" CPI — call it $\text{CPI}_{\text{ideal}}$ — that ignores memory stalls. To model real performance, we split CPI into the ideal execution cost plus the extra cycles lost waiting on memory:
$$
\text{CPU time} = IC * \text{CPI} * CC = IC * \underbrace{(\text{CPI}_{\text{ideal}} + \text{Average memory stall cycles})}_{\text{CPI}_{\text{stall}}} * CC
$$
where:
$$
\text{Average memory stall cycles} = \text{access\_rate} * \text{miss\_rate} * \text{miss\_penalty}
$$
*Notes:* it's generally assumed that cache **hit** time is already folded into $\text{CPI}_{\text{ideal}}$ for load/store instructions (i.e., a hit doesn't cost anything "extra" beyond normal execution — only *misses* add stall cycles). Also, plain "CPI" (without a subscript) in this context specifically means the ideal CPI, not $\text{CPI}_{\text{stall}}$.

### Definitions: hit rate, hit time, miss rate, miss penalty

- **Hit Rate**: the percentage of memory accesses found at a given level of the hierarchy.
- **Hit Time**: the time to retrieve data on a hit at a given level — this includes both the time to *determine* hit/miss, and the time to actually access/transmit the block.
- **Miss Rate**: the percentage of memory accesses *not* found at a given level, i.e. $1 - \text{Hit Rate}$.
- **Miss Penalty**: the *total* time required to search for and retrieve the requested block from a lower (slower) level, once a miss has occurred. It bundles together: time to determine hit/miss, time to access the block in the lower level, time to transmit that block back to the current level, time to insert the block into the current level's cache, and time to pass the block along to whatever requested it.

Crucially: **Hit Time ≪ Miss Penalty** — a hit is cheap, a miss is expensive, often by orders of magnitude (as the latency table above shows starkly for, e.g., an L1 hit vs. a page fault to disk).

### Why the numbers matter — impacts of cache performance
$$
\text{CPI}_{\text{stall}} = \text{CPI}_{\text{ideal}} + \text{Avg. mem. stall cycles}, \qquad \text{Avg. mem. stall cycles} = \text{access\_rate} * \text{miss\_rate} * \text{miss\_penalty}
$$
- As processors get faster (higher clock rate, lower $\text{CPI}_{\text{ideal}}$), the *relative* cost of a cache miss actually goes **up** — because miss penalty is measured in *clock cycles*, and a faster clock means more cycles pass during the same fixed real-world memory-access time. In other words: making the CPU faster alone can make cache misses hurt proportionally more, not less (another face of the Memory Wall).
- The lower $\text{CPI}_{\text{ideal}}$ already is, the more pronounced the *relative* effect of a cache miss becomes on total CPI, for the same reason.
- For a fixed CPU and fixed main memory technology, miss penalty is essentially a hardware constant you can't change from the software/compiler side.
- What *can* be affected by the program and compiler are the stall cycles themselves, via: (a) the raw *number* of memory accesses (fewer accesses → fewer chances to miss), and (b) the *miss rate*, which is directly a measure of how well the access pattern respects locality.
- This whole calculation assumes an **idealized cache**: a single level of cache sitting between CPU and main memory. Real systems with multiple cache levels need the extended AMAT treatment below.

### Worked example: CPI with memory stalls

**Setup:** $\text{CPI}_{\text{ideal}} = 2$, miss penalty = 100 cycles, 36% of instructions are loads/stores, miss rate = 4%.

**Q: average memory stall cycles? $\text{CPI}_{\text{stall}}$?**
$$
\text{Memory-stall cycles} = 36\% * 4\% * 100 = 1.44
$$
$$
\text{CPI}_{\text{stall}} = 2 + 1.44 = 3.44
$$
**Extension — split into separate instruction-cache and data-cache miss rates** (2% I-cache miss rate, 4% D-cache miss rate): now every instruction fetch (100% of instructions, since every instruction must be fetched) can miss in the I-cache, while only the 36% load/store instructions can miss in the D-cache:
$$
\text{Memory-stall cycles} = 1 * 2\% * 100 + 36\% * 4\% * 100 = 2 + 1.44 = 3.44
$$
$$
\text{CPI}_{\text{stall}} = 2 + 3.44 = 5.44
$$
**Extension — what if $\text{CPI}_{\text{ideal}}$ drops to 1, and the data-cache miss rate rises to 5% (I-cache miss rate still 2%)?**
$$
\text{Memory-stall cycles} = 1 * 2\% * 100 + 36\% * 5\% * 100 = 2 + 1.80 = 3.80
$$
$$
\text{CPI}_{\text{stall}} = 1 + 3.80 = 4.80
$$
Wait — the slides give $\text{CPI}_{\text{stall}} = 5.80$ (i.e., stall cycles of $3.80$ but using $\times 100$ differently: $36\% * 5\% * 100 = 1.80$ was recomputed on the slide as $3.80$ total combined with the instruction term). Recomputing carefully from the slide's own arithmetic: $1 * 2\% * 100 + 36\% * 5\% * 100 = 2 + 1.8 = 3.8$, and the slide states $\text{CPI}_{\text{stall}} = 2 + 3.80 = 5.80$ — meaning the slide kept $\text{CPI}_{\text{ideal}} = 2$ here rather than the earlier-proposed reduction to 1 (i.e., this final part of the example evaluates the effect of the *miss-rate increase alone*, holding $\text{CPI}_{\text{ideal}}$ at its original value of 2, not stacking it on top of the CPI-reduction scenario). Net takeaway of the example as a whole: small percentage-point changes in miss rate, or in $\text{CPI}_{\text{ideal}}$, can shift total CPI substantially once you multiply through by a 100-cycle miss penalty — this is the practical reason miss rate reduction is such a high-leverage target for both hardware and software optimization.

### Average Memory Access Time (AMAT) — a time-based alternative metric

$\text{CPI}_{\text{stall}}$ measures cost in *cycles specific to one CPU's pipeline design*. **AMAT** measures cost in *time*, averaged over both hits and misses, which makes it more directly comparable across different designs:
$$
\text{Cache Miss Rate} = \frac{\text{number of cache misses}}{\text{total number of cache references (accesses)}}, \qquad \text{Miss rate + Hit rate} = 1.0 \, (100\%)
$$
$$
\text{AMAT} = \text{Time for a Hit} + \text{Miss Rate} * \text{Miss Penalty}
$$
Here, **Miss Penalty** specifically means the access time of the memory level *one below* the level in question (i.e., what you pay *in addition* to the hit-time cost, on top of the fact that you already tried and failed at the current level).

**Worked example:** 200 ps clock, miss penalty = 50 clock cycles, miss rate = 0.02, cache access time (hit time) = 1 clock cycle.
$$
\text{AMAT} = 1 + 0.02 * 50 = 2 \text{ clock cycles}, \quad 2 * 200\text{ps} = 400\text{ ps}
$$
### AMAT with multiple cache levels

With more than one level of cache, each level has its own speed, so miss penalty must be computed recursively, level by level — the "miss penalty" for one level *is itself* the AMAT-style cost of the level below it:
$$
\text{L1 Miss Penalty} = \text{L2 Hit Time} + \text{L2 Miss Rate} * \text{L2 Miss Penalty}
$$
$$
\text{L2 Miss Penalty} = \text{L3 Hit Time} + \text{L3 Miss Rate} * \text{L3 Miss Penalty}
$$
$$
\text{L3 Miss Penalty} = \text{Main Memory Hit Time (usually)}
$$
giving the recursive **AMAT**:
$$
\text{AMAT} = \text{L1 Hit Time} + \text{L1 Miss Rate} * \text{L1 Miss Penalty}, \quad \text{where L1 Miss Penalty} = \text{L2 Hit Time} + \text{L2 Miss Rate} * \text{L2 Miss Penalty}, \; \dots
$$
**Worked example:** 200 ps clock cycle; L1 hit time = 1 cycle, L1 miss rate = 2%; L2 hit time = 5 cycles, L2 miss rate = 5%; main memory access time = 100 cycles.

*Without an L2 cache* (L1 misses go straight to main memory):
$$
\text{AMAT} = 1 + 0.02 * 100 = 3 \text{ cycles}, \quad 3 * 200\text{ps} = 600\text{ ps}
$$
*With an L2 cache* (L1 misses go to L2 first, which usually hits, only occasionally falling through to main memory):
$$
\text{AMAT} = 1 + 0.02 * (5 + 0.05 * 100) = 1 + 0.02 * 10 = 1.2 \text{ cycles}, \quad 1.2 * 200\text{ps} = 240\text{ps}
$$
Adding the L2 cache more than halves AMAT here (600 ps → 240 ps), even though L1's own hit time and miss rate didn't change at all — this is the concrete payoff of building a multi-level hierarchy rather than jumping straight from a small L1 to slow main memory.

## Locality and Cache

This final section ties locality analysis back to *actual quantitative* hit/miss counts, given concrete cache parameters — moving from "does this loop have good locality, qualitatively" to "exactly how many hits and misses will this loop cause."

### Advanced temporal locality — it depends on relative sizes

Revisit the nested-loop example from Exercise 1/2 above:
```c
int sumarray(int[][] a, int M, int N) {
    int i, j, sum = 0;
    for (i = 0; i < M; i++)
        for (j = 0; j < N; j++)
            sum += a[i][j];
    return sum;
}
```
*Recall:* whether there's meaningful temporal locality tied to `M` depends on the size of `N` (i.e., on how much data sits *between* successive reuses of anything tied to the outer loop variable). More precisely: depending on the size of the cache *and* the size of `N`, it's actually possible for the temporally-relevant data to survive in cache across outer-loop iterations. Specifically: if $\text{sizeof(int)} \times (N + 6) \le \text{cache size}$, then `M` (or rather, whatever data is associated with tracking the outer loop across its full inner sweep) can still remain resident in cache by the time it's needed again. (This assumes an LRU cache policy, a data-only cache with no register usage muddying the picture, and the "+6" accounting for a handful of other live scalars like `sum`, `i`, `j` alongside the row of `N` ints.) The point: locality isn't just a property of the *code* — it's a joint property of the code **and** the actual sizes involved relative to the cache, so the same loop can be locality-friendly on one machine/cache-size/`N` combination and locality-hostile on another.

### Advanced spatial locality — quantifying cold miss rate from block size

In a row-major language:

- **Stepping through columns within one row** (`for (i = 0; i < N; i++) sum += a[0][i];`): this accesses successive elements of size $k$ bytes each. If the cache block size $B > k$ bytes, spatial locality is exploited, because multiple successive elements land in the same block. The resulting **cold miss rate** works out to $k / B$ (bytes-per-element over bytes-per-block) — i.e., you pay a miss only once every $B/k$ elements. Typically $k = 4$ or $8$ bytes (32-bit or 64-bit values) and block size $B = 8k$ or $16k$ bytes.
- **Stepping through rows within one column** (`for (i = 0; i < n; i++) sum += a[i][0];`): assuming the number of columns in `a` is large, this accesses widely-separated (distant) elements — each step jumps a full row's width in memory. There's **no spatial locality** here: cold miss rate = 1 (i.e., 100% — a miss on literally every access), because no two consecutive accesses ever land in the same block.

### Fully worked spatial-locality example

**Setup:** array `a` has row-major `INT4` (4-byte int) elements and is cache-aligned; cache capacity = 4 KB; cache block size = 32 bytes; all local variables live in registers (not cache, so they don't consume cache capacity or generate their own misses).

```c
int i, sum = 0, N = 16384;
for (i = 0; i < N; i++)
    sum += a[i];
```

Reasoning:
- This is **stride-1** access to `a`.
- Each 32-byte block holds $32 / 4 = 8$ ints (since each `int` is 4 bytes).
- So there's exactly **one cold miss per block** — the first access to any given block misses, but the next 7 accesses to that same block are all hits (since the whole block got pulled into cache on the miss).
- Total cold misses: $(1/8) \times 16384 = \mathbf{2048}$ cache misses.
- Total cache hits: $16384 - 2048 = \mathbf{14336}$ cache hits.

(Note that the cache's 4KB capacity never actually becomes a binding constraint in this particular example — with only cold misses occurring and no data being re-requested after eviction, this example doesn't generate any *capacity* or *conflict* misses; it's purely illustrating how block size alone determines the cold-miss rate for a stride-1 scan.)

## Summary

- The core goal is memory that is simultaneously **large, cheap, and fast** — but building all of memory out of SRAM (as fast as L1) at the size of main memory would be unreasonably expensive and physically large.
- The **memory hierarchy** is the solution: successively lower (slower, bigger, cheaper) levels hold the "most used" data from the level above, refreshed from the next level up as needed.
- This entire scheme only works because it exploits **temporal and spatial locality** in real programs — without locality, caching would provide no benefit, since there'd be no way to predict which small subset of data to keep close to the CPU.
- This is an instance of a more general architectural principle sometimes called **"do the common case fast, worry less about the exceptions"** (a RISC design principle): optimize aggressively for cache *hits* (the common case) since they dominate total accesses when locality holds, and accept that misses (the exception) will be comparatively expensive.
- **Challenge for the programmer/compiler**: since the hardware can only exploit locality that's actually present in the code, developing *cache-friendly* (efficient) programs — e.g. correct loop ordering matching array layout, as in the copymatrix and nested-loop examples throughout these notes — is a real, learnable skill with measurable performance consequences (recall the ~2.5x slowdown from loop order alone in the opening example).
