## The Basics

### Components of a Computer
A computer is made of three coupled units:
- **CPU** — contains the **control** (directs execution) and **datapath** (does the computing). These internals are called the **micro-architecture** and are covered later in the course; for now the CPU is treated as a black box.
- **Memory** — stores instructions and data.
- **Devices** — input/output.

CPU and memory are tightly coupled where performance is concerned — this becomes clear by the end of the chapter (memory access time is one of the three factors that determines running time, below).

### Terminology Review
- **CPU** — Central Processing Unit.
- **Processor** — sometimes used interchangeably with CPU, sometimes refers specifically to the circuitry doing the processing within the CPU.
- **Memory word** — the standard unit of memory moved/operated on at once, typically 32 or 64 bits.
- **RAM** — Random Access Memory; can be static (SRAM, faster/pricier) or dynamic (DRAM, needs periodic refresh).
- **HDD** — Hard Disk Drive.
- **SSD** — Solid State Drive; persists data without power, smaller and faster than an HDD.

### Programmer's View of CPU Performance
Running time of a program is determined by three things:
1. **Clock rate** of the CPU (e.g. 3.4 GHz)
2. **Type of instructions** executed — e.g. addition/subtraction is cheaper than multiplication/division. This affects the average **clock cycles per instruction (CPI)**.
3. **Memory access time** — recall the processor–memory speed gap.

Assuming clock rate is fixed, a programmer can still affect performance through instruction choice and memory access patterns.

> **Aside — real numbers (6th-gen Intel, 2015–2019):**
> - 32-bit integer division ≈ 26 cycles vs. a logical bit shift ≈ 1 cycle (`i /= 2` vs `i >>= 1`)
> - Float division ≈ 14 cycles vs. float multiplication ≈ 5 cycles (`x /= 2.0f` vs `x *= 0.5f`)
> - Classic example: the [Fast Inverse Square Root](https://en.wikipedia.org/wiki/Fast_inverse_square_root) trick from *Quake*, which swaps an expensive division/sqrt for cheap bit tricks.

### Understanding and Analyzing Performance
Several layers all affect real-world performance, not just algorithmic complexity:
- **Algorithmic analysis** — Big-O is an idealized abstraction; two different $O(n^2)$ algorithms can have very different real running times.
- **Programming language / compiler / architecture** — determine which actual machine instructions get generated; different compilers/languages → different instruction mix → different performance.
- **Processor and memory** — determine how fast instructions execute and how fast data moves.
- **I/O system (incl. OS)** — determines I/O speed.

### Why We Need Performance Metrics
Two practical perspectives:
- **Purchasing** — which machine has the best cost, or best cost-for-performance?
- **Design** — which design option gives the best performance improvement, or the best improvement-per-cost?

Either way we need (i) a basis for comparison and (ii) metrics for evaluation.

### CPU Performance: Latency
**Latency** (aka response time, aka execution time) is the time between start and completion of a task — matters most to a general end user.

$$\text{performance}_X = \frac{1}{\text{execution\_time}_X}$$

If $X$ is $n$ times faster than $Y$:
$$\frac{\text{performance}_X}{\text{performance}_Y} = \frac{\text{execution\_time}_Y}{\text{execution\_time}_X} = n$$

Latency can also be used to compare a *single instruction's* speed across different CPUs.

### CPU Performance: Throughput
**Throughput** is the total amount of work done per unit time — matters most to someone like a data-center operator running many jobs.
- Throughput depends on which code is being run, just like latency does.
- Reducing response time *usually* improves throughput, but not always — other factors matter too (task scheduling, memory bandwidth, etc.).

### CPU Performance: Clock Frequency
Clock frequency is a **code-agnostic** measure — a higher clock rate is *usually* better, but the micro-architecture and ISA (instruction set architecture) strongly affect how much work gets done per cycle (i.e., efficiency). So clock rate alone doesn't determine which CPU is actually faster.

> **Worked example:**
> - CPU A: 3 GHz, division takes 20 cycles → $20 / 3\text{GHz} = 6.66\,\text{ns}$
> - CPU B: 2 GHz, division takes 10 cycles → $10 / 2\text{GHz} = 5.00\,\text{ns}$
>
> Despite the lower clock rate, **CPU B is faster for this operation** — a smaller number of cycles-per-op won out over raw frequency.

### CPU Clocking
CPUs are synchronous digital systems governed by a **clock**, which synchronizes internal circuits, memory state, and data movement.
- **Clock period / clock cycle (CC)** — duration of one cycle; determines processor "speed" (but *not necessarily* latency or throughput directly). E.g. $250\text{ps} = 0.25\text{ns} = 250\times10^{-12}\text{s}$.
- **Clock frequency / rate (CR)** — cycles per second, the inverse of the clock period. E.g. $3.0\text{GHz} = 3000\text{MHz} = 3.0\times10^{9}\text{Hz}$.

$$CR = \frac{1}{CC}$$

The length of the clock period is set by the internal circuit/micro-architecture design (covered later with datapaths and pipelining).

### CPU Time
Important distinction: **wall time** (elapsed real-world time) vs. **CPU time** (time actually spent executing your task — excludes waiting on I/O or time given to other processes).

$$\text{CPU execution time}_{\text{program}} = \#\text{CPU clock cycles}_{\text{program}} \times \text{clock cycle}$$
$$\text{CPU execution time}_{\text{program}} = \frac{\#\text{CPU clock cycles}_{\text{program}}}{\text{clock rate}}$$

→ Performance can be improved by shortening the clock cycle **or** by reducing the number of clock cycles a program needs.

## Clock Cycles per Instruction (CPI)

### Instruction Performance
$$\#\text{CPU clock cycles}_{\text{program}} = \#\text{Instructions}_{\text{program}} \times \text{Average \# cycles per instruction}$$

- **CPI** — average number of clock cycles each instruction takes.
- Different instruction types take different amounts of time (recall the division vs. shift example).
- CPI is a useful way to compare two different micro-architecture implementations of the *same* ISA.
- Computed by averaging over each instruction type's frequency and cycle cost.
- "Average CPI" and "Effective CPI" mean the same thing — usually just called **CPI**.
- $CPI_i$ denotes the CPI of a specific instruction type $i$.

### The Classic Performance Equation
$$\text{CPU time} = \text{Instruction\_count} \times CPI \times \text{clock\_cycle}$$
$$\text{CPU time} = \frac{\text{Instruction\_count} \times CPI}{\text{clock\_rate}}$$

**Time is the only complete and reliable measure of performance.** Reducing instruction count in a redesign can backfire if it increases CPI or lengthens the clock cycle enough to offset the gain — the design with fewer instructions is not automatically the fastest.

### Worked Example — Effective CPI
$$\text{Overall effective CPI} = \sum_{i=1}^{n} \frac{CPI_i \times IC_i}{IC}$$

| Op | Inst. Freq | $CPI_i$ | Freq × $CPI_i$ |
|---|---|---|---|
| ALU | 50% | 1 | 0.5 |
| Load | 20% | 5 | 1.0 |
| Store | 10% | 3 | 0.3 |
| Branch | 20% | 2 | 0.4 |
| **Sum** | | | **2.2** |

**Scenario 1 — better data cache drops average load CPI from 5 to 2:**
New load contribution = $0.2 \times 2 = 0.4$ → new total CPI = **1.6**.
Speedup: $2.2 / 1.6 = 1.375$ → **37.5% faster**.

**Scenario 2 — branch prediction saves 1 cycle off branch (CPI 2 → 1):**
New branch contribution = $0.2 \times 1 = 0.2$ → new total CPI = **2.0**.
Speedup: $2.2 / 2.0 = 1.1$ → **10% faster**.

**Scenario 3 — on top of Scenario 2, two ALU instructions execute at once (effectively halving ALU's contribution):**
New ALU contribution = $0.5 / 2 = 0.25$ → new total CPI = **1.95**.
Speedup: $2.2 / 1.95 \approx 1.128$ → **12.8% faster**.

### Understanding Program Performance
$$\text{CPU Time} = \text{Instructions} \times \frac{\text{Clock cycles}}{\text{Instruction}} \times \frac{\text{Seconds}}{\text{Clock cycle}}$$

Overall program performance depends on algorithm, language, compiler, architecture, and hardware — each affects different terms of the equation:

| Factor | Instruction_count | CPI | clock_cycle |
|---|:---:|:---:|:---:|
| Algorithm | ✓ | ✓ | |
| Programming language | ✓ | ✓ | |
| Compiler | ✓ | ✓ | |
| ISA | ✓ | ✓ | ✓ |
| Processor organization | | ✓ | ✓ |

### Check Yourself — Worked Problem
A Java app runs **15 s**. A new compiler emits **0.6×** as many instructions but raises CPI by **1.1×**. New runtime?

$$\text{Time}_2 = IC_1 \times 0.6 \times CPI_1 \times 1.1 \times CC_1 = \text{Time}_1 \times 0.6 \times 1.1 = 15 \times 0.6 \times 1.1 = 9.9\,\text{s}$$

**Answer: 9.9 seconds.** (Not $15 \times 0.6/1.1$ or $15\times1.1/0.6$ — both instruction count *and* CPI scale the time multiplicatively in the same direction, since CPU time is a product of all three terms.)

## Power, Trends, Limitations

### Power Trends
CMOS (the technology underlying modern CPU circuitry) has a simplified power equation:
$$\text{Power} = \text{Capacitive load} \times \text{Voltage}^2 \times \text{Frequency switched}$$

Historically (per the slide chart, 1982–2012): capacitive load rose ~30×, voltage dropped from 5V → 1V, and switching frequency rose ~1000×. Clock rates climbed steadily from ~12.5 MHz (80286, 1982) to ~3.4 GHz+ (Core i5 Ivy Bridge, 2012), while power draw rose sharply through the Pentium 4 era (~103W) before leveling off/declining in later Core-series chips (~77–95W) as designers optimized for power efficiency.

### Reducing Power — Worked Example
New CPU: 85% of old capacitive load, 15% lower voltage, 15% lower frequency.

$$\frac{P_{new}}{P_{old}} = \frac{C_{old}\times0.85 \times (V_{old}\times0.85)^2 \times F_{old}\times0.85}{C_{old}\times V_{old}^2\times F_{old}} = 0.85^4 \approx 0.52$$

→ roughly **halves power draw**. (Voltage's squared term makes it the most powerful lever.)

### The Power Wall
- Chips simply cannot dissipate/consume much more power.
- Shrinking transistors → more transistors per chip → **greater power density** (harder to cool).
- Voltage and capacitive load are already difficult to reduce further.
- Removing excess heat is a major engineering bottleneck.

This is a core reason clock-rate scaling stalled in the mid-2000s (visible in the "Relative Performance vs VAX-11" chart: ~52%/year growth 1986–2003, dropping to ~22%/year 2003–2012).

### Multi-Processors to the Rescue
With single-core scaling hitting the power wall (Moore's Law slowing for single-thread performance), the industry's answer was **parallelism** — multi-core chips.
- More than one processor per chip; big win for the OS and for running multiple independent processes concurrently.
- Getting a **single** process to benefit requires **explicit parallel programming** — unlike instruction-level parallelism (pipelining/multi-issue), which the hardware exploits automatically and invisibly to the programmer.
- Parallel programming is hard: thread management, load balancing, and optimizing communication/synchronization all add complexity.

## Benchmarks and Profiling

### SPEC CPU Benchmark
**SPEC** (Standard Performance Evaluation Corp) develops standardized benchmarks (CPU, I/O, Web, etc.) meant to represent "typical" real workloads.

**SPEC CPU** specifically:
- Measures elapsed time on a curated set of programs with negligible I/O, isolating CPU performance.
- Scores are normalized against a reference machine.
- Overall score = **geometric mean** of the per-program execution-time ratios:
$$\sqrt[n]{\prod_{i=1}^{n}\text{Execution time ratio}_i}$$
- Split into **CINT** (integer workloads) and **CFP** (floating-point workloads).

**CINT2006 example (Intel Core i7 920):** a table of 12 benchmark programs (perl, bzip2, gcc, mcf, go, hmmer, sjeng, libquantum, h264avc, omnetpp, astar, xalancbmk) each report instruction count, CPI, clock cycle time, execution time, a reference time, and a per-program SPECratio (reference/execution). The overall score is the **geometric mean of the individual SPECratios = 25.7**. Note the wide spread in per-program ratios (14.9–190.0) — reinforcing that "performance" is workload-dependent, not a single universal number.

### Profiling Tools
Tools for measuring where time/resources actually go in a running program:
- **gprof** — static instrumentation.
- **cachegrind**, **Dtrace** — dynamic instrumentation.
- **perf** (Linux) — based on **event sampling** using hardware performance counters (cycles, cache misses, branch misses, instructions-per-cycle, and hundreds of other CPU-specific events). Full event list: Intel® 64 and IA-32 SDM, Appendix A. See also the [perf user guide](https://perf.wiki.kernel.org/index.php/Tutorial).

### Exercise 1 — `copymatrix1` vs `copymatrix2`
Two functions copy an `n×n` matrix `src` into `dst`, differing only in loop order:
- `copymatrix1`: outer loop over `i` (rows), inner loop over `j` (columns) — accesses `dst[i][j]`/`src[i][j]` **row-major**, matching how C stores 2D arrays in memory.
- `copymatrix2`: outer loop over `j`, inner loop over `i` — accesses memory **column-major**, jumping around in memory on each inner-loop iteration.

**`perf stat -e cycles -e cache-misses` results:**

| | cycles | cache-misses | time elapsed |
|---|---|---|---|
| copymatrix1 (row-major) | 557,458,379 | 2,071,981 | 0.211 s |
| copymatrix2 (col-major) | 1,418,374,698 | 3,980,687 | 0.534 s |

**Row-major (`copymatrix1`) wins** — roughly **2.5× faster**, with about half the cache misses. This is a direct illustration of *why memory access pattern matters for performance* (per the "CPU and memory are highly coupled" point from the start of the chapter): sequential/contiguous access exploits **spatial locality** and the cache, while the column-major traversal strides across memory and thrashes the cache.

### Exercise 2 — `lower1` vs `lower2`
Both functions lowercase a C string `s` in place, differing in how they compute string length:
- `lower1`: calls `strlen(s)` **inside the loop condition**, i.e., on *every* iteration.
- `lower2`: calls `strlen(s)` **once**, caches it in `n`, then loops using `n`.

**`perf stat -e cycles -e cache-misses` results:**

| | cycles | cache-misses | time elapsed |
|---|---|---|---|
| lower1 (strlen every iteration) | 131,658,606,345 | 19,799 | 43.20 s |
| lower2 (strlen cached once) | 24,846,861 | 12,013 | 0.011 s |

**`lower2` is dramatically faster — over 5000× faster in cycles/time**, despite similar (low) cache-miss counts. The bottleneck here isn't memory locality — it's **redundant computation**: `strlen` is $O(n)$, so calling it inside a loop that runs `n` times turns a linear-time function into an accidental $O(n^2)$ algorithm. This is a classic case of instruction-count/algorithmic inefficiency dominating performance, distinct from the cache-driven effect in Exercise 1.

## Summary / Key Takeaways
- Performance is fundamentally about **time**; instruction count, CPI, and clock cycle time each capture one piece of it, and improving one can hurt another.
- **Latency** and **throughput** are different, sometimes-competing goals.
- Clock frequency alone is a poor proxy for real performance — micro-architecture and ISA matter just as much.
- Power scales with $V^2 \times f$, which is why voltage/frequency scaling stalled (the **power wall**) and the industry pivoted to **multi-core** parallelism.
- Benchmarks like **SPEC CPU** give standardized, workload-based comparisons rather than raw clock numbers.
- Real profiling (Exercises 1 & 2) shows two *distinct* performance pitfalls: poor **memory locality** (cache misses) and **redundant computation** (hidden algorithmic complexity) — both matter, and neither is visible from source code alone without measurement.
