## Encapsulation

Encapsulation is a core concept of Object-Oriented Programming (OOP). It means:

- Bundling the data (attributes) and the methods (functions) that operate on that data into a single unit — a **class**.
- Restricting access to some of an object's components so its internal state is protected from direct access or modification by other objects.

Encapsulation is really doing two things at once: packaging (grouping related data and behavior together) and protection (controlling who is allowed to touch that data). It's the reason a class can be thought of as a self-contained "black box" — callers interact with what it exposes, not with how it's built internally.

### Data Hiding and Access Modifiers

Data hiding is enforced through access modifiers, which control who can see and use a class's members:

|Modifier|Accessible from|
|---|---|
|`private`|Only within the class it is declared in|
|`protected`|The class itself, and any derived (subclass) classes|
|`public`|Anywhere, including outside the class|

The general pattern: attributes are usually kept `private`, while the methods needed to interact with them are made `public`. This way the class controls all access to its own data — nothing outside the class can reach in and change state directly.

### Getter and Setter Methods

Since attributes are private, a class exposes **getter** and **setter** methods to read and modify them safely. This indirection matters because it lets the class run validation or extra logic every time data changes, instead of allowing an uncontrolled direct write.

```cpp
class Person {
private:
    string name;  // Private data member

public:
    // Getter method to access the private member 'name'
    string getName() {
        return name;
    }

    // Setter method to modify the private member 'name'
    void setName(string newName) {
        name = newName;
    }
};
```

### Worked Example: BankAccount

A fuller example showing validation logic inside setters — this is the real payoff of encapsulation, not just hiding a variable for its own sake:

```cpp
class BankAccount {
private:
    double balance;  // Private attribute, can't be accessed directly from outside

public:
    // Constructor
    BankAccount(double initial_balance) {
        if (initial_balance >= 0)
            balance = initial_balance;
        else
            balance = 0;
    }

    // Getter method for balance (read-only access)
    double getBalance() {
        return balance;
    }

    // Setter method to deposit amount (write access with validation)
    void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    // Setter method to withdraw amount (write access with validation)
    void withdraw(double amount) {
        if (amount > 0 && amount <= balance) {
            balance -= amount;
        }
    }
};

int main() {
    BankAccount account(1000);  // Initial balance of 1000

    // Access balance through the public interface
    cout << "Initial Balance: $" << account.getBalance() << endl;

    account.deposit(500);  // Deposit 500
    cout << "After Deposit: $" << account.getBalance() << endl;

    account.withdraw(200);  // Withdraw 200
    cout << "After Withdrawal: $" << account.getBalance() << endl;

    return 0;
}
```

Key point: `balance` is private and can **only** be reached through `getBalance`, `deposit`, and `withdraw`. Every change to `balance` is therefore controlled and validated (e.g. you can never withdraw more than the balance, or set a negative starting balance) — something that would be impossible to guarantee if `balance` were a public field anyone could overwrite directly.

### Benefits of Encapsulation

- **Security** — prevents unintended interference or manipulation of an object's data.
- **Maintainability** — the internal implementation of a class can change freely without affecting other parts of the code, as long as the public interface stays the same. This is a big deal in practice: it means you can rewrite _how_ a class works internally (e.g. switch from an array to a hash map) without breaking any code that uses the class, since callers never depended on the internals in the first place.
- **Reusability** — well-encapsulated classes with clear interfaces are easier to reuse in other contexts because their behavior is self-contained and predictable.

## Conceptual Integrity

Successful systems should have **conceptual integrity**: a consistent and unified design vision across the entire project, where a small set of design decisions is controlled centrally to maintain consistency, and the system's complexity is hidden behind a simpler, unified interface — the same way a class in OOP hides its internal workings behind public methods.

- It isolates the core complexity of the design so the rest of the team can focus on implementation without worrying about the underlying design decisions.
- **Modularization** is how this is achieved in practice: breaking a large system down into smaller, manageable modules, similar to how classes and objects encapsulate complexity in OOP. Each module exposes a well-defined interface while keeping its internal details hidden.

In short, encapsulation is the mechanism at the class level; conceptual integrity is the same idea applied at the scale of an entire system or codebase.

## Coupling Choices in OOP: From Concretions to Abstractions

**Coupling** is how tightly one class depends on another. Why it matters: the tighter the coupling, the harder a system is to change, extend, or test, because a change to one class forces changes everywhere that depends on it. The lecture presents four ways a class can depend on another, ordered from worst to best.

There are two independent questions being combined here:

1. **What do you depend on?** A concrete class, or an abstraction (interface)?
2. **Who creates the dependency?** Does the class instantiate it itself (`new`/construct it internally), or is it handed in ("injected") from outside?

### 1) Concrete + Instantiate (worst)

The class hardcodes a concrete type and creates it itself. This is the **tightest coupling and least flexible** option — the dependency is baked in with no way to change it without editing the class's source code.

```cpp
class Paypal {
public:
    void pay(double amount) {
        std::cout << "Paid $" << amount << " with Paypal\n";
    }
};

class Checkout {
    Paypal processor;  // OWNED concrete member (composition)
public:
    void process(double amount) {
        processor.pay(amount);
    }
};

int main() {
    Checkout c;
    c.process(50.0);  // Hardwired to Paypal
}
```

`Checkout` can never use anything but `Paypal` — swapping payment providers means rewriting `Checkout` itself.

### 2) Concrete + Inject ⚠️

The class still depends on a concrete type, but that concrete object is now passed in from outside rather than created internally. This **avoids the creation problem**, but the class is **still tied to a concretion** — you can supply a different `Paypal` instance, but you still can't supply anything that isn't a `Paypal`.

```cpp
class Checkout {
    Paypal& processor;  // Aggregation: holds reference
public:
    Checkout(Paypal& p) : processor(p) {}
    void process(double amount) {
        processor.pay(amount);
    }
};

int main() {
    Paypal paypal;
    Checkout c(paypal);  // Inject concrete object
    c.process(75.0);
}
```

### 3) Abstract + Instantiate ⚠️

The class now depends on an abstraction (an interface with pure virtual functions), which **gains polymorphism** — but the class still creates the concrete implementations internally, so it's **still rigid**. You've added flexibility in _type_ but not in _choice_: the class decides for itself which concrete implementations to use.

```cpp
class IPaymentProcessor {
public:
    virtual ~IPaymentProcessor() = default;
    virtual void pay(double amount) = 0;
};

class Paypal : public IPaymentProcessor {
public:
    void pay(double amount) override {
        std::cout << "Paid $" << amount << " with Paypal\n";
    }
};

class Stripe : public IPaymentProcessor {
public:
    void pay(double amount) override {
        std::cout << "Paid $" << amount << " with Stripe\n";
    }
};

class Checkout {
    Paypal p1;   // Composition: creates concretes
    Stripe p2;
public:
    Checkout() : p1(), p2() {}
    void process(double amount) {
        p1.pay(amount/2);
        p2.pay(amount/2);
    }
};

int main() {
    Checkout c;
    c.process(100.0);
}
```

Even though `IPaymentProcessor` exists as an abstraction, `Checkout` is still the one deciding to construct `Paypal` and `Stripe` directly — so it's still coupled to those concrete classes at compile time.

### 4) Abstract + Inject (best, DIP) ✅

The class depends **only** on the abstraction, and concrete implementations are supplied ("injected") from outside at runtime. This is the **Dependency Inversion Principle (DIP)** — the most flexible and testable option, because `Checkout` never needs to know or care which concrete class it's working with.

```cpp
class Checkout {
    IPaymentProcessor& processor;  // Aggregation: depends on abstraction
public:
    Checkout(IPaymentProcessor& p) : processor(p) {}
    void process(double amount) {
        processor.pay(amount);  // calls chosen concrete's pay()
    }
};

int main() {
    Paypal paypal;
    Stripe stripe;

    Checkout c1(paypal);  // inject Paypal
    Checkout c2(stripe);  // inject Stripe

    c1.process(120.0);  // "Paid $120 with Paypal"
    c2.process(80.0);   // "Paid $80 with Stripe"
}
```

Any future payment provider just needs to implement `IPaymentProcessor` and can be plugged into `Checkout` with zero changes to `Checkout` itself. This is also what makes unit testing easy: in a test, you can inject a fake/mock `IPaymentProcessor` instead of a real payment gateway.

### Summary Table

|Style|What happens|Relationship|
|---|---|---|
|Concrete + Instantiate|Checkout creates a Paypal itself|Composition|
|Concrete + Inject|Checkout receives a Paypal|Aggregation|
|Abstract + Instantiate|Checkout depends on IPaymentProcessor but still `new`s concretes|Composition|
|Abstract + Inject (best)|Checkout depends on IPaymentProcessor and gets concretes injected|Aggregation|

> Note on terminology: **composition** here means the containing class owns and creates the member object (their lifetimes are tied together); **aggregation** means the containing class merely holds a reference/pointer to an object created and owned elsewhere. Moving from composition toward aggregation, and from concrete types toward abstractions, is what drives a design from rigid to flexible.

## Interfaces vs Parameters vs Concretes: When to Use What

The question of "should I make an interface / subclass for this?" comes down to **what kind of variation you're dealing with**.

### Interfaces

Use an interface when the variation is **behavioral** — i.e., different implementations need genuinely different algorithms/logic.

- Enables polymorphism and the Dependency Inversion Principle (DIP).
- Consumers couple to the abstraction, not the concrete class.
- Result: flexible, extensible, testable code.

### Parameters

Use a parameter (constructor argument or field) when the variation is **only data** — e.g. numbers, labels, config strings — not behavior.

- Avoids "subclass explosion," where you end up creating a new subclass for every trivial difference that's really just a different value.
- Keep a single class and configure it via constructor arguments or fields.
- Lightweight and clear — the simplest fix, and normally the _first_ thing to reach for before creating a class hierarchy.

### Concretes

The smallest/simplest approach: no abstraction at all.

- Fine for tiny apps or one-off utilities.
- Trade-off: consumers are tied directly to the concrete implementation, so it's harder to extend or swap behavior later without touching every caller.

### Rule of Thumb

> Behavior → Interface Data → Parameter Toy/simple case → Concrete

## Worked Case Study: Logger

This case study walks through the same problem three times, each version demonstrating one of the rules above.

### Case 1: Abstraction exists, but variation is only data (the wrong way)

Two loggers exist under a shared `ILogger` interface, but the _only_ thing that differs between them is a string prefix — this is data, not behavior, so creating separate subclasses for it is unnecessary overhead ("pointless separate class"):

```cpp
class ILogger {
public:
    virtual ~ILogger() = default;
    virtual void log(const std::string& msg) const = 0;
};

// Both print to console; only the prefix differs → this is *just data*.
class DebugLogger : public ILogger {
public:
    void log(const std::string& msg) const override {
        std::cout << "[DEBUG] " << msg << "\n";
    }
};

class ErrorLogger : public ILogger {
public:
    void log(const std::string& msg) const override {
        std::cout << "[ERROR] " << msg << "\n";
    }
};

int main() {
    DebugLogger d;  // pointless separate class
    ErrorLogger e;  // pointless separate class
    d.log("System booted.");
    e.log("Disk failure!");
}
```

**The right way** — keep the interface (for future behavioral variation, e.g. a real file-based logger later), but replace the two near-identical subclasses with **one parameterized concrete class**, since the only difference between them is data:

```cpp
class ILogger {
public:
    virtual ~ILogger() = default;
    virtual void log(const std::string& msg) const = 0;
};

// One class; the *level* is DATA (constructor arg).
class ConsoleLogger : public ILogger {
    std::string level;
public:
    explicit ConsoleLogger(std::string lvl) : level(std::move(lvl)) {}
    void log(const std::string& msg) const override {
        std::cout << "[" << level << "] " << msg << "\n";
    }
};

int main() {
    ConsoleLogger debug("DEBUG");  // data = "DEBUG"
    ConsoleLogger error("ERROR");  // data = "ERROR"

    ILogger& l1 = debug;  // callers still couple to the abstraction
    ILogger& l2 = error;

    l1.log("System booted.");
    l2.log("Disk failure!");
}
```

**Lesson:** When variation is only data (e.g. label text), don't make subclasses. Keep the interface, but use one parameterized class.
### Case 2: No abstraction; no subclasses for data variation

An even smaller version of the same idea — skip the interface entirely and just parameterize a single concrete class:

```cpp
class Logger {                              // no interface here
    std::string level;
public:
    explicit Logger(std::string lvl) : level(std::move(lvl)) {}
    void log(const std::string& msg) const {
        std::cout << "[" << level << "] " << msg << "\n";
    }
};

int main() {
    Logger debug("DEBUG");        // data-only variation handled by ctor arg
    Logger error("ERROR");

    debug.log("Starting up...");
    error.log("Something went wrong!");
}
```

**Trade-off:** minimal and fine for tiny apps, but the calling code now depends directly on a concrete type (`Logger`). If a genuinely different logging _behavior_ is needed later (e.g. writing to a file instead of the console), every caller will need to be refactored — there's no interface boundary to isolate that change behind.
### Case 3: With interfaces (behavioral variation + DI)

Now the variation actually **is** behavioral — console output vs. writing to a file are genuinely different algorithms — so separate classes under a shared interface are justified, and the high-level consumer (`AuditService`) depends on the abstraction and receives a concrete implementation via constructor injection (DI):

```cpp
// Abstraction
class ILogger {
public:
    virtual ~ILogger() = default;
    virtual void log(const std::string& msg) const = 0;
};

// Concrete #1: Console behavior
class ConsoleLogger : public ILogger {
public:
    void log(const std::string& msg) const override {
        std::cout << "[CONSOLE] " << msg << "\n";
    }
};

// Concrete #2: File behavior (different algorithm)
class FileLogger : public ILogger {
    std::string filename;
public:
    explicit FileLogger(std::string fn) : filename(std::move(fn)) {}
    void log(const std::string& msg) const override {
        std::ofstream out(filename, std::ios::app);
        out << "[FILE] " << msg << "\n";
    }
};

// High-level consumer depends on abstraction and gets a concrete via DI
class AuditService {
    ILogger& logger;                       // injected dependency (aggregation)
public:
    explicit AuditService(ILogger& l) : logger(l) {}
    void record(const std::string& msg) { logger.log(msg); }  // polymorphic call
};

int main() {
    ConsoleLogger console;
    FileLogger file("audit.log");

    AuditService a(console);  // inject console
    AuditService b(file);     // inject file

    a.record("User logged in.");
    b.record("Transaction completed.");
}
```

This is the DIP pattern (Abstract + Inject) applied to logging: `AuditService` never needs to know whether it's writing to the console or a file, so new logging destinations (e.g. a network logger) can be added later without changing `AuditService` at all.

### Case Study Takeaways

- **Example 1:** Keep the abstraction, but handle data-only variation with one parameterized class — don't create subclasses for mere labels.
- **Example 2:** The smallest possible approach: no abstraction, one parameterized concrete class (callers now depend directly on the concretion).
- **Example 3:** When behavior genuinely differs, use interfaces + dependency injection to couple to the abstraction and swap implementations freely.

## Lecture Summary

- Encapsulation bundles data and behavior into a class and restricts direct access to internal state.
- Why coupling matters in OOP: dependencies between classes shape how flexible a system is to change.
- Data variation → use parameters, not subclasses.
- Behavioral variation → use interfaces (abstractions).
- Four dependency patterns, from worst to best: Concrete+Instantiate, Concrete+Inject, Abstract+Instantiate, Abstract+Inject (DIP).
- Core principle: **couple to abstractions, not concretions.**
