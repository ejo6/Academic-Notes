## Objects & Classes

- **Class** — a blueprint/template defining the attributes and behaviors an object will have.
- **Object** — an instance of a class. You can create many objects from one class.
- **Attributes** (data members) — variables that store an object's state.
- **Methods** (member functions) — functions that define an object's behavior.

> [!example] Car class
> `Car` is the class. Attributes: `color`, `speed`, `model`. Methods: `accelerate()`, `brake()`, `getSpeed()`. A specific Toyota or Ford is an **object** (instance) of `Car`.

## Access Specifiers

| Specifier | Access |
|---|---|
| `private` | Only within the class itself |
| `public` | Accessible from outside the class |
| `protected` | Accessible within the class **and** derived classes, but not from outside |

## Constructors & Destructors
- **Constructor** — special method that runs when an object is created; used to initialize state.
- **Destructor** — runs when an object is destroyed; used to release/clean up resources (memory, file handles, etc.).

```cpp
class Car {
public:
    Car(std::string carModel, int carYear) {   // constructor
        model = carModel;
        year = carYear;
    }
    void displayInfo() {
        std::cout << "Model: " << model << ", Year: " << year << std::endl;
    }
private:
    std::string model;
    int year;
};

int main() {
    Car myCar("Toyota", 2022);
    myCar.displayInfo();
    return 0;
}
```

## Process for Designing Classes & Objects

A basic OOD workflow for turning a problem into a class model:

1. **Identify objects** — scan the problem domain for real-world entities/concepts.
   - *e.g. online shopping system → `Customer`, `Product`, `Order`, `ShoppingCart`*
2. **Define attributes & methods** for each object.
   - *e.g. `Product` → attributes `name`, `price`, `stockQuantity`; methods `getPrice()`, `updateStock()`*
3. **Determine relationships** between objects:
   - **Association** — objects know about / reference each other (`Customer` has an `Order`).
   - **Aggregation** — one object is composed of other objects (`Order` contains multiple `Product`s).
   - **Inheritance** — a specialized "is-a" relationship (`Admin`, `RegularUser` inherit from `User`).

> [!tip] Additional info — Aggregation vs. Composition
> The slides lump these together under "aggregation," but in UML they're distinct and this distinction shows up constantly in design-pattern discussions:
> - **Aggregation** ("has-a", weak ownership): the contained object can exist independently of the container (e.g. a `Department` has `Employee`s — employees still exist if the department is dissolved).
> - **Composition** ("owns-a", strong ownership): the contained object's lifetime is tied to the container (e.g. a `House` is composed of `Room`s — destroy the house, the rooms go with it).
> Worth keeping straight since UML class diagrams use different arrowheads for each (hollow diamond = aggregation, filled diamond = composition).

## OOP vs. Functional Programming (FP)

Core idea: **OOP models state that changes over time; FP models transformations of immutable data.**

| Aspect      | OOP                                                                           | Functional Programming                                                    |
| ----------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Focus       | Objects (data + behavior bundled)                                             | Functions (transform data)                                                |
| State       | Mutable, lives inside objects                                                 | Immutable — new data returned, nothing modified in place                  |
| Modularity  | Classes, object hierarchies                                                   | Functions, composition of functions                                       |
| Concurrency | Harder — shared mutable state → race conditions, deadlocks, need locks        | Easier — no shared mutable state, so functions can run in parallel safely |
| Abstraction | Objects encapsulate state + expose behavior via public methods                | Higher-order functions, function composition, pure functions              |
| Reuse       | Inheritance, polymorphism                                                     | Higher-order functions (pass/return/store functions)                      |
| Typical use | UIs, games, business apps — systems that map naturally to real-world entities | Data transformation, scientific computing, concurrent/stateless systems   |

**Same example, both paradigms:**

```cpp
// OOP — state lives inside the object and is mutated in place
class Account {
    double balance;
public:
    Account(double initialBalance) : balance(initialBalance) {}
    void deposit(double amount) { balance += amount; }     // mutates state
    void withdraw(double amount) { if (balance >= amount) balance -= amount; }
    double getBalance() const { return balance; }
};
```

```cpp
// Functional — no stored state; each call returns a new value
double deposit(double balance, double amount) {
    return balance + amount;               // returns new balance, doesn't mutate
}
double withdraw(double balance, double amount) {
    return (balance >= amount) ? balance - amount : balance;
}
```

> [!tip] Additional info — why this matters beyond the exam
> This distinction is exactly why languages like C++/Java lean OOP by default but increasingly borrow FP features (lambdas, `std::function`, `const`/immutability, `map`/`filter`-style algorithms in `<algorithm>`). Modern "good" OOP design often *minimizes* mutable state for the same reasons FP favors immutability — fewer places for bugs to hide, easier to reason about, easier to test. Keep this in mind for the design-patterns portion of the course (e.g. why immutable value objects are often recommended even in OOP codebases).

## Cohesion & Coupling

Two of the most important **quality metrics** for a design — expect these to come back explicitly when Single Responsibility and Dependency Inversion are covered later.

### Cohesion
> How closely related the responsibilities *within* a single class/module are.

- **High cohesion** (desirable): a class does one focused job. Ties directly to the **Single Responsibility Principle** (later lecture).
  - *e.g. `ShoppingCart` with `addItem()`, `removeItem()`, `calculateTotal()` — everything is cart-related.*
- **Low cohesion**: a class's responsibilities are scattered/unrelated → harder to maintain, changes ripple unpredictably.
- Why it matters: easier to understand, easier to maintain, more reusable.

### Coupling
> How dependent one module/class is on another.

- **Low coupling** (desirable): modules are mostly independent; changing one doesn't force changes elsewhere. Ties to the **Dependency Inversion Principle** (later lecture).
- Why it matters: easier maintenance, more flexibility, easier to test in isolation.

### The four combinations

| | Low Coupling | High Coupling |
|---|---|---|
| **High Cohesion** | ✅ Ideal — focused classes, minimal dependencies | Well-organized internally, but too dependent on other modules |
| **Low Cohesion** | Independent, but internally disorganized | ❌ Worst case — disorganized *and* highly dependent |

> [!tip] Additional info — a quick smell test
> If you struggle to name a class without using "and" or "manager" (e.g. `OrderAndPaymentManager`), that's usually a low-cohesion smell. If changing one class routinely forces you to edit several others, that's a high-coupling smell. Both are useful heuristics during the course project's design phase, since you'll be graded on design quality.

## Advantages of OOP

| Advantage | What it means | Example |
|---|---|---|
| **Modularity** | System broken into self-contained, focused classes | `ShoppingCart`, `Order`, `Payment` developed independently |
| **Reusability** | Base classes extended via inheritance/polymorphism instead of rewritten | `Vehicle` base class reused for `Car`, `Bike`, `Truck` |
| **Encapsulation** | Internal state hidden, accessed only through controlled methods | `BankAccount` exposes `deposit()`/`withdraw()`, keeps `balance` private |
| **Maintainability** | Separation of concerns — bugs/changes isolated to one class | Fixing `Payment` doesn't break `ShoppingCart` or `Order` |
| **Extensibility** | Add new classes/methods without touching existing code (Open/Closed Principle, later lecture) | Add a feature without modifying working code |
| **Polymorphism** | Different classes treated via a common interface | `PaymentMethod` interface → `CreditCardPayment`, `PayPalPayment`, `CryptoPayment` |
| **Inheritance** | Share/reduce duplication via hierarchical relationships | `Character` base class → `Warrior`, `Mage` |
| **Team collaboration** | Clear interfaces let teams work on separate classes in parallel | One team owns `User`, another owns `Transaction` |
| **Security / access control** | Access modifiers restrict what can touch sensitive data | `BankTransaction` limits access based on user roles |
| **Scaling** | Independent components can scale independently | Microservices: scale `PaymentService` without touching `UserService` |
| **Debugging & testing** | Self-contained classes can be tested in isolation | Mock `Payment`/`Shipping` to unit-test `Order` alone |

## Summary

- OOP = model the problem as interacting objects that bundle state + behavior.
- Design process: identify objects → define attributes/methods → determine relationships.
- OOP trades off against FP mainly around **mutable state**: OOP embraces it (with encapsulation to manage it), FP avoids it.
- **Cohesion** (within a class) should be high; **coupling** (between classes) should be low — this pairing is the single biggest lever on maintainability, and will recur all course via SRP and DIP.
- The "advantages of OOP" list is really a preview of design patterns/principles to come (SRP, OCP, DIP, etc.) — worth mentally bookmarking which advantage maps to which future topic.eeww
