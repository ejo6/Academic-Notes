# Templates, Specialization, Mixins, and CRTP

## What Are Templates?

Templates let you write **generic code** — code that works with any type — instead of duplicating the same logic once per type. The compiler does the duplication for you, automatically, only for the types you actually use.

There are two basic kinds:

- **Function templates**
- **Class templates**

### Function Templates

```cpp
template <typename T>
T max(T a, T b) {
    return (a > b) ? a : b;
}
```

- `template <typename T>` tells the compiler "this function works for any type `T`."
- `T` is a **placeholder type** — it isn't resolved until the function is actually called.
- The compiler infers `T` from the arguments you pass in:

```cpp
max(3, 7);      // T = int    → 7
max(4.5, 2.1);  // T = double → 4.5
max('a', 'z');  // T = char   → 'z' (compares ASCII values)
```

> **Note:** `typename` here could equally be written as `class` (`template <class T>`) — the two keywords are interchangeable in this position for historical reasons. `typename` is generally preferred in modern C++ because `class` is also a keyword used to _define_ classes, which can read confusingly.

### Class Templates

```cpp
template <typename T>
class Box {
private:
    T value;
public:
    void set(T val) { value = val; }
    T get() const { return value; }
};
```

Usage:

```cpp
Box<int> intBox;
intBox.set(10);
std::cout << intBox.get(); // 10

Box<std::string> strBox;
strBox.set("hello"); // string literal "hello" (const char*) implicitly converts to std::string
std::cout << strBox.get(); // hello
```

### Template Instantiation

A template isn't compiled into machine code by itself — it's a _blueprint_. The first time you use it with a concrete type (e.g. `Box<int>`), the compiler generates a brand-new class specifically for that type:

```cpp
class Box_int {
private:
    int value;
public:
    void set(int val) { value = val; }
    int get() const { return value; }
};
```

This is called **template instantiation**, and it happens once per distinct type you actually use (`Box<int>` and `Box<std::string>` generate two separate classes behind the scenes). This is also _why_ template code that is never instantiated for a given type is never fully type-checked for that type — the compiler only checks the code paths it actually generates.

### Template Parameters

You aren't limited to a single type parameter — templates can take **multiple** type parameters, just like a function can take multiple value parameters:

```cpp
template <typename T, typename U>
T add(T a, U b) {
    return a + b;
}
```

- This lets **one function** (`add`) work across combinations of types, instead of writing `int add()`, `double add()`, `stringAdd()`, etc. separately.
- The two parameters (`T`, `U`) don't have to match: `add(3, 4.5)` → `T = int`, `U = double`.

**Careful with the return type.** In the version above, the return type is fixed to `T` — the type of the _first_ argument — not whatever type the addition naturally produces. This matters:

```cpp
auto result = add(3, 4.5); // mathematically 7.5, but returned as T = int → truncated to 7
add(5, 'A'); // 'A' is char, promotes to its ASCII value 65 → 5 + 65 = 70
```

> The general lesson: template code still obeys all of C++'s normal type-conversion/promotion rules underneath — templates decide _which_ code gets generated, not how arithmetic or conversions behave once it's generated. Locking the return type to `T` can silently discard precision (as with the `double` truncating to `int` above) if you're not paying attention to what your template parameters actually resolve to.

## Policy-Based Design

**Policy-Based Design** is a template pattern where you inject custom _behavior_ into a class through a **template parameter**, instead of through inheritance or virtual functions.

- No inheritance hierarchy is required — the "policy" classes don't need to share a common base class.
- All wiring happens through **compile-time composition**: the compiler picks the right code path when the template is instantiated, so there's **zero runtime overhead** (no vtable lookup, unlike a virtual function).

### Worked Example — Pluggable Logging Policies

```cpp
// Policy 1: logs to the console
class ConsoleLogger {
public:
    static void log(const std::string& message) {
        std::cout << "[Console] " << message << std::endl;
    }
};

// Policy 2: logs nothing (a no-op, useful for disabling logging entirely)
class NullLogger {
public:
    static void log(const std::string&) { /* do nothing */ }
};

// Policy 3: (simulated) logs to a file
class FileLogger {
public:
    static void log(const std::string& message) {
        std::cout << "[File] (simulated) " << message << std::endl;
    }
};

// The class that *uses* a policy — the policy is a template parameter
template <typename LogPolicy>
class Printer {
public:
    void print(const std::string& msg) {
        LogPolicy::log("Printing: " + msg); // delegate to whichever policy was chosen
        std::cout << msg << std::endl;
    }
};
```

```cpp
Printer<ConsoleLogger> consolePrinter;
consolePrinter.print("Hello from ConsoleLogger!");

Printer<NullLogger> silentPrinter;
silentPrinter.print("This one has no logging");

Printer<FileLogger> filePrinter;
filePrinter.print("This message is logged as if to a file");
```

Note the policy classes use `static` methods — since there's no shared base class or interface, `Printer` just needs to call `LogPolicy::log(...)` directly on the type, with no object of that policy ever being instantiated.

|Feature|Why it matters|
|---|---|
|Compile-time switch|No virtual function overhead|
|Reusable policies|Write once, reuse across many classes|
|No inheritance|Doesn't require shared base classes|
|Flexible|Swap behavior just by changing a template argument|

> **Where you've likely already used this:** the STL itself is built on policy-based design — `std::vector<T, Allocator>`'s second (usually defaulted, rarely-specified) template parameter is a _memory-allocation policy_. Same idea as the logger example, just for `new`/`delete` behavior instead of logging.

## CRTP — Curiously Recurring Template Pattern

**CRTP** is when a base class is templated **on its own derived class** — the child passes _itself_ as the template argument to its parent.

```cpp
class Derived : public Base<Derived> { ... };
```

This gives you:

- **Static (compile-time) polymorphism** — behaves like virtual functions, but resolved at compile time, so there's no runtime cost.
- **Code reuse** — shared logic lives once, in the base.
- **Compile-time interface enforcement** — the base can require the derived class to implement certain methods, and you'll get a compile error if it doesn't, rather than a runtime crash.

### Worked Example — Logging via CRTP

```cpp
// Base class takes the derived class as a template parameter
template <typename Derived>
class LoggerBase {
public:
    void log() {
        // static_cast lets the base "reach down" and call Derived's own method
        std::cout << "[LOG] " << static_cast<Derived*>(this)->getData() << std::endl;
    }
};

class TemperatureSensor : public LoggerBase<TemperatureSensor> {
public:
    std::string getData() const { return "Temperature: 22.5°C"; }
};

class PressureSensor : public LoggerBase<PressureSensor> {
public:
    std::string getData() const { return "Pressure: 101.3 kPa"; }
};
```

```cpp
TemperatureSensor temp;
temp.log();       // [LOG] Temperature: 22.5°C

PressureSensor pressure;
pressure.log();   // [LOG] Pressure: 101.3 kPa
```

**How the `static_cast` trick works:** `LoggerBase<Derived>::log()` doesn't know at the time it's _written_ what `getData()` will do — it just knows that whatever `Derived` ends up being, it will have a `getData()` method. The `static_cast<Derived*>(this)` reinterprets `this` (a `LoggerBase<Derived>*`) as a `Derived*`, which is safe specifically _because_ `Derived` publicly inherits from `LoggerBase<Derived>` — so the cast is guaranteed to be valid, and it costs nothing at runtime (unlike `dynamic_cast`, which does a runtime type check).

### CRTP vs. Virtual Functions

|Feature|CRTP|Virtual Function|
|---|---|---|
|Performance|Fast (no vtable)|Slower (needs vtable lookup)|
|Runtime polymorphism|Not supported|Supported|
|Compile-time checking|Enforced via templates|Not enforced until runtime|
|Flexibility|Template magic (mixins, etc.)|Inheritance hierarchy|

> The big trade-off to flag here: CRTP gives up **runtime polymorphism**. You can't put a `TemperatureSensor` and a `PressureSensor` in the same `std::vector<LoggerBase*>` and call `log()` on each through a common base pointer the way you could with virtual functions — `LoggerBase<TemperatureSensor>` and `LoggerBase<PressureSensor>` are two entirely different, unrelated types once instantiated. CRTP is the right tool when you know all your types **at compile time**; virtual functions are the right tool when you need to decide _which_ concrete type you're dealing with **at runtime** (e.g., loading a plugin, deserializing an object of unknown type).

## Mixins

A **mixin** is a class that adds reusable behavior to another class **without being its parent** in a traditional (single-purpose) inheritance hierarchy. Think of mixins as plug-in building blocks you stack together to give a class extra abilities — logging, timestamping, serialization, comparison operators, etc. — each as an independent, composable unit.

### Worked Example — A Single Mixin

```cpp
template <typename Derived>
class LoggerMixin {
public:
    void log(const std::string& msg) {
        std::cout << "[LOG] " << msg << std::endl;
    }
};

class MyComponent : public LoggerMixin<MyComponent> {
public:
    void run() {
        log("Running MyComponent task...");
        std::cout << "Doing actual work..." << std::endl;
    }
};
```

```cpp
MyComponent comp;
comp.run();
// [LOG] Running MyComponent task...
// Doing actual work...
```

Notice this _is_ CRTP under the hood (`LoggerMixin<MyComponent>` takes `MyComponent` as its own template parameter) — the difference between "a mixin" and "CRTP" is more about **intent** than mechanism: CRTP is the general technique of a self-referencing template base; a mixin is what you call it when you're using that technique specifically to bolt on an independent, reusable _feature_ rather than to define a core type relationship.

### Stacking Multiple Mixins

Because mixins don't need to share a common base, a class can inherit from **several** of them at once — this is where mixins really distinguish themselves from a rigid single-parent inheritance chain:

```cpp
template <typename Derived>
class TimestampMixin {
public:
    void printTime() {
        std::cout << "[TIME] 2025-09-17 16:00" << std::endl;
    }
};

class AdvancedComponent
    : public LoggerMixin<AdvancedComponent>,
      public TimestampMixin<AdvancedComponent> {
public:
    void run() {
        printTime();
        log("Advanced task running...");
    }
};
```

```
[TIME] Wed Sep 18 17:06:34 2025
[LOG] Advanced task running...
```

> **Small inconsistency worth noting:** the `TimestampMixin::printTime()` code as written just prints a hard-coded string (`"2025-09-17 16:00"`), but the sample output shown is a different, dynamically-generated timestamp (`Wed Sep 18 17:06:34 2025`) — the kind of string you'd get from `std::time`/`ctime` rather than a literal. That mismatch is just a slide artifact (the "live" output was probably captured from a slightly different version of the code that actually calls the C time API); it isn't something you need to reconcile, just don't take the printed output as a literal trace of the printed code.

**Multiple inheritance and the diamond problem:** stacking mixins is a form of multiple inheritance, which in general C++ code can lead to the classic "diamond problem" (ambiguous shared state when two parents both inherit from a common grandparent). Mixins mostly sidestep this in practice because each mixin is templated on `Derived` — `LoggerMixin<AdvancedComponent>` and `TimestampMixin<AdvancedComponent>` are _different, unrelated template instantiations_, not two paths back to one shared base, so there's no ambiguous shared state to resolve.

### Mixins vs. Inheritance vs. CRTP

|Feature|Mixins|Classic Inheritance|CRTP|
|---|---|---|---|
|Multiple behaviors|Easily stackable|Often hard to scale|Usually used _inside_ a single mixin/feature|
|Performance|Compile-time (fast)|Virtual table overhead (if using virtuals)|No runtime overhead|
|Flexibility|Choose features modularly|Rigid hierarchy|Great for enforcing APIs|

> Read this table as: **CRTP is the mechanism**, and **mixins are one particular _use_ of that mechanism** (the "modular, stackable feature" use case). Classic (single-hierarchy, often virtual-function-based) inheritance is the alternative you reach for when you genuinely need runtime polymorphism instead of compile-time composition.

## Template Specialization

**Template Specialization** lets you provide a **custom implementation** of a template for one specific type, while keeping a generic default for everything else. This is useful when a template works fine generically for most types, but a particular type needs different logic (a different internal representation, a different print format, an optimization that only applies to that type, etc.).

### Full Specialization — Function Template

```cpp
// Primary (generic) template
template <typename T>
void printType(const T& value) {
    std::cout << "Generic type: " << value << std::endl;
}

// Full specialization for std::string
template <>
void printType<std::string>(const std::string& value) {
    std::cout << "Specialized string type: " << value << std::endl;
}
```

```cpp
printType(42);                  // Generic type: 42
printType(3.14);                // Generic type: 3.14
printType(std::string("Hi"));   // Specialized string type: Hi
```

`template <>` signals "this is a specialization, not a new generic template" — since the type is now fixed (`std::string`), there's no placeholder `T` left to declare.

### Full Specialization — Class Template

```cpp
// Generic (primary) template
template <typename T>
class Storage {
public:
    void print(const T& data) {
        std::cout << "Generic Storage: " << data << std::endl;
    }
};

// Full specialization for T = bool
template <>
class Storage<bool> {
public:
    void print(bool data) {
        std::cout << "Specialized Storage: " << (data ? "true" : "false") << std::endl;
    }
};
```

```cpp
Storage<int> s1;
s1.print(123);   // Generic Storage: 123

Storage<bool> s2;
s2.print(true);  // Specialized Storage: true
```

This is a common, practical use of specialization: `bool` prints as `1`/`0` by default via `std::cout`, so a specialization lets you print `"true"`/`"false"` instead, only for that one type, without touching the generic template at all.

### Partial Specialization — Customizing for a _Category_ of Types

Where full specialization targets one exact type (`bool`, `std::string`), **partial specialization** targets a _pattern_ of types — e.g., "any pointer type," rather than one specific pointer type.

```cpp
// Primary (generic) template
template <typename T>
class Wrapper {
public:
    void print() { std::cout << "Generic Wrapper" << std::endl; }
};

// Partial specialization: matches any pointer type (int*, double*, ...)
template <typename T>
class Wrapper<T*> {
public:
    void print() { std::cout << "Pointer Wrapper" << std::endl; }
};
```

```cpp
Wrapper<int> a;
a.print();   // Generic Wrapper

Wrapper<int*> b;
b.print();   // Pointer Wrapper
```

Note that a partial specialization still has a `template <typename T>` header (unlike a full specialization's bare `template <>`) — `T` isn't fully pinned down, only the _shape_ (`T*`) is. The compiler picks the most specific matching version available: generic `Wrapper<T>` for ordinary types, `Wrapper<T*>` for any pointer type.

> **Terminology note:** partial specialization is only available for **class** templates in standard C++ — you cannot partially specialize a _function_ template the same way (you'd use function overloading instead to get an equivalent effect).

### When to Use Template Specialization

Reach for specialization when:

- You need a generic default behavior, **but** want different logic for a handful of specific types (e.g. `bool`, `char*`).
- You want **compile-time dispatch** based on type (the compiler picks the right version automatically, no `if`/`switch` on a type tag at runtime).
- You're implementing **type traits** or other template-metaprogramming logic — a large amount of the standard library's type-trait machinery (`std::is_pointer`, `std::is_same`, etc.) is itself built out of full and partial specializations.

## Summary

|Topic|Key Idea|
|---|---|
|Function/Class Templates|Write one generic definition; the compiler generates a concrete version (**instantiation**) per type actually used|
|Template Parameters|Templates can take multiple, independent type parameters (`T`, `U`, ...); watch out for the return type fixing precision/conversion behavior|
|Policy-Based Design|Inject behavior via a template parameter instead of inheritance — compile-time composition, zero runtime cost, no shared base class required|
|CRTP|A base class templated on its own derived class (`Derived : Base<Derived>`) → static polymorphism, enforced at compile time, no vtable|
|Mixins|Independent, stackable "plug-in" classes (built using the CRTP mechanism) that add behavior without a rigid single-parent hierarchy|
|Template Specialization|Full specialization overrides one exact type; partial specialization overrides a pattern of types (e.g. all pointers); both resolve at compile time|
