## Process Concept

The terms **job** and **process** are used almost interchangeably in OS literature.

A **process** is a program in execution; process execution must progress in **sequential fashion** (a single process executes one instruction at a time, in order — it does not jump around arbitrarily).

A process is made up of several distinct parts in memory:

- **Text section** — the program code itself.
- **Current activity**, including the **program counter** (a register holding the address of the next instruction to execute) and the other processor registers.
- **Stack** — containing temporary data such as function parameters, return addresses, and local variables. It grows and shrinks as functions are called and return.
- **Data section** — containing global variables.
- **Heap** — containing memory dynamically allocated during run time (e.g., via `malloc` in C or `new` in Java).

> **Context:** The stack and heap both grow, but in opposite directions, toward each other from opposite ends of the process's address space — this is why the diagram below shows them meeting in the middle. If they ever collide, that's a stack overflow or heap exhaustion.

![[Screenshot 2026-09-16 at 10.25.29 AM.png|180]]

**Program vs. process** — a critical distinction:

- A **program** is a **passive** entity: an executable file stored on disk. It's just data sitting there, doing nothing.
- A **process** is **active**: the program becomes a process once its executable file is loaded into memory and begins executing, at which point it has a program counter, registers, and a call stack that change over time.
- **One program can be several processes.** For example, if multiple users each run the same text editor at the same time, each is a separate process, even though they're all instances of the same underlying program on disk.

### Process in Memory

A process's address space is laid out (conceptually) as, from the lowest memory address (0) to the highest (max):

1. **Text** — program code (fixed size, read-only)
2. **Data** — global variables (fixed size)
3. **Heap** — grows _upward_ as memory is dynamically allocated
4. **(gap of unused memory)**
5. **Stack** — grows _downward_ as function calls are made

The heap and the stack grow toward each other across the gap of unused memory, which allows both to expand as needed without a fixed, wasteful pre-allocation for either.

## Process State

As a process executes, it changes **state**, reflecting its current activity:

- **new** — the process is being created.
- **running** — instructions are being executed (only one process per CPU core can be in this state at any instant).
- **waiting** — the process is waiting for some event to occur (e.g., I/O completion, a signal from another process).
- **ready** — the process is waiting to be assigned to a processor; it could run immediately if given the CPU.
- **terminated** — the process has finished execution.

### Diagram of Process State

The transitions between states form a cycle:

- **new → ready**: via "admitted" (the OS finishes setting up the process and adds it to the ready queue).
- **ready → running**: via "scheduler dispatch" (the CPU scheduler picks this process to run).
- **running → ready**: via "interrupt" (e.g., the process's time slice expires, and it's forced back to the ready queue so another process can run).
- **running → waiting**: via "I/O or event wait" (the process requests something, like disk I/O, and must wait).
- **waiting → ready**: via "I/O or event completion" (whatever the process was waiting for has happened).
- **running → terminated**: via "exit" (the process finishes and asks to be deleted).

> **Context:** Notice a process can never go directly from **waiting** to **running** — it must always pass back through **ready** and wait for the scheduler to dispatch it again, even if the CPU happens to be idle at that instant. This keeps scheduling decisions centralized and consistent.

## Process Control Block (PCB)

Every process is represented in the OS by a **Process Control Block** (also called a **task control block**), which stores all the information the OS needs to manage the process:

- **Process state** — running, waiting, etc.
- **Process number** — the process's unique ID (PID).
- **Program counter** — location of the instruction to execute next.
- **CPU registers** — the contents of all process-specific registers (so execution can resume exactly where it left off).
- **CPU scheduling information** — priorities, pointers to scheduling queues.
- **Memory-management information** — what memory is allocated to the process.
- **Accounting information** — CPU time used, elapsed clock time since start, time limits.
- **I/O status information** — I/O devices allocated to the process, list of open files.

> **Context:** The PCB is essentially the "identity card" of a process — everything the OS needs to pause a process and later resume it as if nothing happened is stored here. This is what makes multitasking possible: the PCB captures a complete snapshot of a process's state.

### CPU Switch From Process to Process

When the CPU switches from running process P0 to process P1:

1. P0 is executing; an **interrupt or system call** occurs.
2. The OS **saves P0's state into PCB0** (this takes some time, during which neither process is running — the CPU is "idle" from either process's perspective).
3. The OS **reloads state from PCB1**, and P1 begins executing.
4. Later, another interrupt or system call occurs, and the reverse happens: P1's state is saved into PCB1, and P0's state is reloaded from PCB0, resuming P0 exactly where it left off.

This save/reload cycle is the mechanical basis of a **context switch** (detailed further below).

## Threads

So far, each process has been described as having a single thread of execution (one program counter, one instruction stream).

Consider instead having **multiple program counters per process** — this allows multiple locations in the program to execute "at once" (concurrently). Multiple threads of control within a single process are called **threads**.

If a process has multiple threads, the PCB must be extended to store multiple sets of thread details (multiple program counters, multiple register sets, etc.), since each thread needs its own execution context even though all threads in a process share the same address space (text, data, heap).

> **Context:** Threads are a deep topic covered more fully in a later chapter, but the key intuition introduced here is: a process is a container of resources (memory, open files), while a thread is a unit of CPU scheduling/execution _within_ that container. Multiple threads in one process share memory, which makes communication between them cheap (compared to separate processes, which don't share memory by default), but also makes them vulnerable to interfering with each other if not synchronized properly.

## Process Representation in Linux

In Linux, each process is represented by the C structure `task_struct`. Some key fields include:

```c
pid_t pid;               /* process identifier */
long state;               /* state of the process */
unsigned int time_slice;  /* scheduling information */
struct task_struct *parent;      /* this process's parent */
struct list_head children;       /* this process's children */
struct files_struct *files;      /* list of open files */
struct mm_struct *mm;            /* address space of this process */
```

All of the `task_struct`s for currently existing processes are linked together (conceptually, via a doubly-linked structure), and the kernel tracks which one is `current` — the currently executing process.

## Process Scheduling

The overall goal of process scheduling is to **maximize CPU use** by quickly switching processes onto the CPU (this is what enables time-sharing between multiple processes).

The **process scheduler** selects among available processes for the next execution on the CPU. It maintains several **scheduling queues**:

- **Job queue** — the set of _all_ processes in the system.
- **Ready queue** — the set of all processes residing in main memory that are ready and waiting to execute.
- **Device queues** — the set of processes waiting for a particular I/O device (each device typically has its own queue).

Processes **migrate** among these queues over their lifetime — e.g., a process might move from the ready queue to the CPU, then to a device queue while waiting on disk I/O, then back to the ready queue once that I/O completes.

### Ready Queue and Device Queues (structurally)

Each queue is implemented as a linked list of PCBs, with a **queue header** holding pointers to the **head** and **tail** of the list. For example, the ready queue's header points to the first and last PCB currently waiting for the CPU; a disk's device queue header points to the PCBs of processes waiting on that specific disk. As processes move between states, they're unlinked from one queue and relinked into another.

### Representation of Process Scheduling (Queueing Diagram)

A **queueing diagram** captures the flow of processes between queues and resources:

- A process enters the **ready queue**, and eventually gets dispatched to the **CPU**.
- From the CPU, several things can happen:
    - **I/O request** → process goes to an **I/O queue**, then to the actual **I/O** device, and afterward back to the ready queue.
    - **Time slice expired** → process goes directly back to the ready queue (this is a forced preemption, not a voluntary wait).
    - **Fork a child** → a new **child** process is created and begins executing (typically added to the ready queue).
    - **Wait for an interrupt** → the process waits until an **interrupt occurs**, then eventually returns to the ready queue.

> **Context:** This diagram is essentially a visual generalization of the process state diagram — it shows the OS as a network of queues and services that processes flow through, which is exactly the framing used later when discussing CPU scheduling algorithms (e.g., how long a process waits in the ready queue, how "fair" the scheduling is, etc.).

## Schedulers

- **Short-term scheduler** (or **CPU scheduler**) — selects which process should be executed next and allocates the CPU to it.
    - Sometimes the only scheduler present in a system.
    - Invoked very **frequently** (every few milliseconds), so it must be **fast** — any time spent scheduling is time not spent running user processes.
- **Long-term scheduler** (or **job scheduler**) — selects which processes should be brought into the ready queue (i.e., admitted into the system from a pool of submitted jobs).
    - Invoked **infrequently** (every few seconds or minutes), so it can afford to be slower/more sophisticated.
    - Controls the **degree of multiprogramming** — i.e., how many processes are in memory competing for the CPU at once.

Processes can be broadly characterized by their behavior:

- **I/O-bound process** — spends more time doing I/O than computation; typically has many short CPU bursts (it quickly finishes a small amount of work, then waits on I/O again).
- **CPU-bound process** — spends more time doing computations; has few but very long CPU bursts.

The long-term scheduler strives for a good **process mix** — a healthy balance of I/O-bound and CPU-bound processes, so that both the CPU and I/O devices stay busy rather than one type of resource sitting idle while the system waits on the other.

### Addition of Medium-Term Scheduling

A **medium-term scheduler** can be added if the degree of multiprogramming needs to be _decreased_ (e.g., the system is too overloaded and running too many processes at once is hurting performance). It works by removing a process from memory, storing it on disk, and later bringing it back in from disk to continue execution — this operation is called **swapping**.

The queueing diagram with swapping added shows: partially-executed, swapped-out processes can be **swapped in** to the ready queue, and processes already in the ready queue that need to make room can be **swapped out** to disk instead of continuing to consume memory.

> **Context:** This ties directly back to the Week 2A introduction's mention of virtual memory and swapping — swapping is the _mechanism_, and the medium-term scheduler is the _policy-maker_ deciding when to invoke it.

## Multitasking in Mobile Systems

Mobile operating systems historically handled multitasking differently from desktop systems, largely due to limited screen real estate, memory, and battery constraints:

- **Early versions of iOS** allowed only _one process to run at a time_, with all others suspended. Due to the UI's limited screen space, iOS provides for:
    - A single **foreground** process — controlled directly via the user interface.
    - Multiple **background** processes — in memory and running, but not displayed, and subject to strict limits (e.g., only a single short task, receiving notification of events, or specific long-running tasks like audio playback).
- **Android** runs both foreground and background processes with fewer restrictions. A background process uses a **service** to perform tasks; a service can keep running even if its parent background process is suspended, has no user interface, and uses relatively little memory.

> **Context:** This is a real-world tradeoff between user experience/battery life and process flexibility — full desktop-style multitasking would drain a mobile battery and degrade UI responsiveness much faster, so mobile OS designers historically chose more restrictive models. Modern iOS has relaxed some of these restrictions since this material was written, but the underlying foreground/background distinction remains.

## Context Switch

When the CPU switches to another process, the system must **save the state** of the old process and **load the saved state** for the new process — this is a **context switch**.

- The **context** of a process is represented in its PCB.
- **Context-switch time is pure overhead** — the system does no useful (user-facing) work while switching; it's purely bookkeeping.
- The more complex the OS and the PCB, the longer the context switch takes (more state to save/restore).
- Context-switch time is also dependent on hardware support — some hardware provides multiple sets of registers per CPU, allowing multiple contexts to be loaded at once, which can dramatically reduce switching overhead.

> **Context:** Because context switching is pure overhead, minimizing its frequency and cost is a real performance concern in OS design — this is part of why the short-term scheduler needs to be fast, and why some systems (real-time systems especially) care a great deal about worst-case context-switch latency.

## Operations on Processes

The system must provide mechanisms for **process creation**, **process termination**, and related operations (detailed below).

### Process Creation

A **parent** process creates **children** processes, which in turn create other processes, forming a **tree of processes**. Each process is generally identified and managed via a **process identifier (pid)**.

**Resource sharing options** when a parent creates a child:

- Parent and children share _all_ resources.
- Children share a _subset_ of the parent's resources.
- Parent and child share _no_ resources.

**Execution options:**

- Parent and children execute **concurrently**.
- Parent **waits** until (some or all of) its children terminate.

**Address space options:**

- Child is a **duplicate** of the parent (same program, same data — this is the default with `fork()`).
- Child has an entirely **new program loaded into it**.

**UNIX examples:**

- `fork()` — a system call that creates a new process (the child) as a near-exact duplicate of the calling process (the parent). Both processes continue executing from the point right after the `fork()` call, but `fork()` returns a different value to each: 0 to the child, and the child's actual PID to the parent.
- `exec()` — used after a `fork()` to replace the child process's memory space with an entirely new program. This is how a shell, for instance, creates a new process to run `ls` — it forks a child, and that child then execs into the `ls` program.

The typical flow: `fork()` → the child calls `exec()` to load a new program → the child eventually calls `exit()` → the parent, which has been in `wait()`, resumes.

### C Program Forking a Separate Process

```c
#include <sys/types.h>
#include <stdio.h>
#include <unistd.h>

int main()
{
    pid_t pid;

    /* fork a child process */
    pid = fork();

    if (pid < 0) { /* error occurred */
        fprintf(stderr, "Fork Failed");
        return 1;
    }
    else if (pid == 0) { /* child process */
        execlp("/bin/ls", "ls", NULL);
    }
    else { /* parent process */
        /* parent will wait for the child to complete */
        wait(NULL);
        printf("Child Complete");
    }

    return 0;
}
```

Here, `fork()` is called once but returns _twice_ — once in the parent (returning the child's pid, a positive number) and once in the child (returning 0). The `if/else if/else` branches distinguish which process is executing which piece of code from that single point onward.

### Creating a Separate Process via the Windows API

Windows does not have a direct equivalent of `fork()`; instead, `CreateProcess()` is used, which both creates a new process _and_ loads a specified program into it in one step (combining what UNIX splits into `fork()` + `exec()`):

```c
#include <stdio.h>
#include <windows.h>

int main(VOID)
{
    STARTUPINFO si;
    PROCESS_INFORMATION pi;

    /* allocate memory */
    ZeroMemory(&si, sizeof(si));
    si.cb = sizeof(si);
    ZeroMemory(&pi, sizeof(pi));

    /* create child process */
    if (!CreateProcess(NULL, /* use command line */
        "C:\\WINDOWS\\system32\\mspaint.exe", /* command */
        NULL, NULL, FALSE, 0, NULL, NULL, &si, &pi))
    {
        fprintf(stderr, "Create Process Failed");
        return -1;
    }
    /* parent will wait for the child to complete */
    WaitForSingleObject(pi.hProcess, INFINITE);
    printf("Child Complete");

    /* close handles */
    CloseHandle(pi.hProcess);
    CloseHandle(pi.hThread);
}
```

### Process Termination

A process executes its last statement and then asks the OS to delete it using the **`exit()`** system call.

- This call returns status data from the child to the parent (via `wait()`).
- The process's resources are deallocated by the operating system.

A parent may also terminate the execution of a child process using the **`abort()`** system call. Some reasons a parent might do this:

- The child has exceeded its allocated resources.
- The task assigned to the child is no longer required.
- The parent is exiting, and the operating system does not allow a child to continue if its parent terminates.

Some operating systems do not allow a child to exist if its parent has terminated — in these systems, if a process terminates, all its children must also be terminated. This is called **cascading termination**: all children, grandchildren, and so on are terminated, and the termination is initiated by the operating system itself (not by the children choosing to exit).

The parent process may wait for the termination of a child process using the `wait()` system call. This call returns status information and the pid of the terminated process:

```c
pid = wait(&status);
```

Two special (and generally undesirable) situations can arise:

- **Zombie** — if no parent is waiting (i.e., the parent never invoked `wait()`), a terminated child process is a zombie: it has finished executing, but its exit status and PCB linger in the process table because nobody has collected them.
- **Orphan** — if the parent terminates _without_ invoking `wait()`, the still-running child process is an orphan.

> **Context:** In most UNIX-like systems, orphaned processes are automatically "adopted" by a special ancestor process (often `init` or PID 1), which then calls `wait()` on their behalf so they don't become permanent zombies once they finish. A zombie process technically isn't "using" much (it's not running), but it does still occupy an entry in the process table, and if enough accumulate, they can exhaust the table and prevent new processes from being created — a real operational concern on long-running systems.

### Multiprocess Architecture — Chrome Browser

Many web browsers historically ran as a **single process** (some still do) — a significant downside is that if one website causes trouble (crashes, hangs, security exploit), it can bring down the _entire_ browser.

The **Google Chrome** browser instead uses a **multiprocess** architecture with three types of processes:

- **Browser** process — manages the user interface, disk I/O, and network I/O.
- **Renderer** process — renders web pages, handling HTML and JavaScript. A new renderer process is created for _each website opened_ (each tab/site gets its own).
    - Runs in a **sandbox**, which restricts its disk and network I/O — this minimizes the damage a security exploit in the renderer (e.g., from a malicious website) can do to the rest of the system.
- **Plug-in** process — a separate process for each type of plug-in in use.

> **Context:** This is a direct, practical application of the process-isolation concept covered above: because each process has its own separate memory space by default, a crash or exploit in one renderer process (one tab) doesn't corrupt the memory of the browser process or other tabs' renderer processes. This is precisely why "one misbehaving tab" in Chrome can be closed/killed without taking down your whole browser, unlike in a single-process browser design.

## Interprocess Communication (IPC)

Processes within a system may be **independent** or **cooperating**:

- An **independent** process cannot affect, or be affected by, the execution of another process.
- A **cooperating** process _can_ affect or be affected by other processes, including by sharing data with them.

**Reasons for cooperating processes:**

- **Information sharing** — multiple processes may need access to the same piece of information (e.g., a shared file).
- **Computation speedup** — breaking a task into subtasks that run in parallel (this generally requires multiple processing cores to gain a real speedup).
- **Modularity** — dividing a system into cooperating modules/processes rather than one monolithic program.
- **Convenience** — an individual user might work on several tasks at once (e.g., editing, compiling, printing, and browsing simultaneously).

Cooperating processes need a mechanism for **interprocess communication (IPC)**, of which there are two models:

- **Shared memory**
- **Message passing**

### Communications Models

- **(a) Message passing:** Process A and process B each interact only with the **kernel**, which manages a **message queue** between them. All communication goes _through_ the kernel via `send`/`receive` system calls — there's no direct shared region between the processes' own memory.
- **(b) Shared memory:** A region of **shared memory** sits directly between process A's and process B's memory, and both processes can read/write it directly, without going back through the kernel for every exchange (only the initial setup of the shared region requires kernel involvement).

> **Context:** The trade-off between these two models is fundamental: message passing is simpler to reason about and inherently synchronized (since the kernel mediates), but every exchange incurs a system call/kernel overhead. Shared memory is much faster for large or frequent data exchange (no kernel involvement per read/write), but the _processes themselves_ must handle synchronization to avoid race conditions — which is a much harder problem, addressed by process synchronization techniques (semaphores, locks, etc.) covered in a later chapter.

### Producer-Consumer Problem

A classic paradigm for cooperating processes: the **producer** process produces information that is consumed by a **consumer** process (e.g., a compiler produces assembly code consumed by an assembler; a web server produces HTML consumed by a browser).

- **Unbounded-buffer** — places no practical limit on the size of the buffer between producer and consumer.
- **Bounded-buffer** — assumes a fixed buffer size; the producer must wait if the buffer is full, and the consumer must wait if the buffer is empty.

### Bounded-Buffer — Shared-Memory Solution

Shared data structure:

```c
#define BUFFER_SIZE 10

typedef struct {
    ...
} item;

item buffer[BUFFER_SIZE];
int in = 0;
int out = 0;
```

`in` points to the next free slot to write to; `out` points to the next item to read. This solution is correct but can only actually use `BUFFER_SIZE - 1` elements — one slot must always remain empty, because an "in == out" condition would otherwise be ambiguous between "buffer completely empty" and "buffer completely full."

**Producer:**

```c
item next_produced;
while (true) {
    /* produce an item in next produced */
    while (((in + 1) % BUFFER_SIZE) == out)
        ; /* do nothing (buffer full — busy-wait) */
    buffer[in] = next_produced;
    in = (in + 1) % BUFFER_SIZE;
}
```

**Consumer:**

```c
item next_consumed;
while (true) {
    while (in == out)
        ; /* do nothing (buffer empty — busy-wait) */
    next_consumed = buffer[out];
    out = (out + 1) % BUFFER_SIZE;

    /* consume the item in next consumed */
}
```

> **Context:** Note the `while (...) ;` loops here are a "busy-wait" (also called spinning) — the process actively checks the condition over and over, wasting CPU cycles rather than truly sleeping. This is a simplified illustration; real systems typically use blocking synchronization primitives (semaphores/condition variables, covered later) rather than busy-waiting, which is inefficient.

### IPC — Shared Memory (Details)

Shared memory is an area of memory shared among the processes that wish to communicate.

- The communication itself is under the control of the **user processes**, not the operating system (once the OS sets up the shared region and hands out access, it steps out of the way).
- A major issue is providing a mechanism that will allow the user processes to **synchronize** their actions when they access shared memory — otherwise two processes could read/write the same memory simultaneously and corrupt data (a **race condition**). This synchronization topic is covered in more depth later in the course.

### IPC — Message Passing (Details)

Message passing is a mechanism for processes to communicate _and_ to synchronize their actions, without needing shared variables at all.

- A **message system** lets processes communicate with each other without resorting to shared variables.
- An IPC facility provides (at minimum) two operations: **`send(message)`** and **`receive(message)`**.
- The size of a message can be either fixed or variable.

## Message Passing

If processes P and Q wish to communicate, they need to:

1. Establish a **communication link** between them.
2. Exchange messages via send/receive.

**Implementation issues** that a message-passing system must resolve:

- How are links established?
- Can a link be associated with more than two processes?
- How many links can exist between every pair of communicating processes?
- What is the capacity of a link?
- Is the size of a message that the link can accommodate fixed or variable?
- Is a link unidirectional or bi-directional?

### Implementation of Communication Link

- **Physical** implementation options:
    - Shared memory
    - Hardware bus
    - Network
- **Logical** properties of the link:
    - Direct or indirect
    - Synchronous or asynchronous
    - Automatic or explicit buffering

### Direct Communication

Processes must name each other **explicitly**:

- `send(P, message)` — send a message to process P.
- `receive(Q, message)` — receive a message from process Q.

**Properties of this kind of link:**

- Links are established **automatically** (just by naming the other process).
- A link is associated with **exactly one pair** of communicating processes.
- Between each pair, there exists **exactly one link**.
- The link may be unidirectional, but is usually bi-directional.

### Indirect Communication

Messages are instead directed to and received from **mailboxes** (also called **ports**).

- Each mailbox has a unique id.
- Processes can communicate only if they **share a mailbox**.

**Properties of this kind of link:**

- A link is established only if processes share a common mailbox.
- A link may be associated with **many** processes.
- Each pair of processes may share **several** communication links (one per shared mailbox).
- A link may be unidirectional or bi-directional.

**Operations** available for indirect communication:

- Create a new mailbox (port).
- Send and receive messages through a mailbox.
- Destroy a mailbox.

Primitives are defined as:

```
send(A, message)     — send a message to mailbox A
receive(A, message)  — receive a message from mailbox A
```

**Mailbox sharing** raises an ambiguity: if P1, P2, and P3 all share mailbox A, and P1 sends while P2 and P3 both try to receive, **who gets the message**? Possible solutions:

- Allow a link to be associated with **at most two processes** (removes the ambiguity by limiting sharing).
- Allow only **one process at a time** to execute a receive operation on that mailbox.
- Allow the system to **select arbitrarily** which process receives it, and notify the sender who the receiver was.

## Synchronization

Message passing may be either **blocking** or **non-blocking**:

- **Blocking** is considered **synchronous**:
    - **Blocking send** — the sender is blocked (cannot continue) until the message is received.
    - **Blocking receive** — the receiver is blocked until a message is available.
- **Non-blocking** is considered **asynchronous**:
    - **Non-blocking send** — the sender sends the message and immediately continues on, without waiting.
    - **Non-blocking receive** — the receiver receives either a valid message, or a null message (if none is available), and continues either way.

Different combinations are possible (blocking send with non-blocking receive, etc.). If **both** send and receive are blocking, this special case is called a **rendezvous** — both processes must arrive at the communication point together before either can proceed, much like two people meeting by appointment.

With synchronous (blocking) message passing, the producer-consumer problem becomes trivial to solve correctly, since the send/receive operations themselves handle the necessary waiting:

```c
message next_produced;
while (true) {
    /* produce an item in next produced */
    send(next_produced);
}

message next_consumed;
while (true) {
    receive(next_consumed);
    /* consume the item in next consumed */
}
```

No explicit buffer-full/buffer-empty checking is needed here, unlike the shared-memory version above — the blocking semantics of `send`/`receive` handle synchronization implicitly.

## Buffering

Whether communication is direct or indirect, messages exchanged by communicating processes reside in a temporary **queue of messages attached to the link**. Such queues can be implemented in one of three ways:

1. **Zero capacity** — no messages are queued on a link at all. The sender must wait for the receiver (this is the **rendezvous** case described above).
2. **Bounded capacity** — the link has a finite length of _n_ messages. The sender must wait if the link is full (all _n_ message slots are occupied).
3. **Unbounded capacity** — the link has (conceptually) infinite length. The sender never waits.

## Examples of IPC Systems

### POSIX

**POSIX Shared Memory** — a process first creates a shared memory segment:

```c
shm_fd = shm_open(name, O_CREAT | O_RDWR, 0666);
```

This same call is also used to _open_ an existing segment in order to share it (if the `O_CREAT` flag finds it already exists, it just opens it). The process then sets the size of the object:

```c
ftruncate(shm_fd, 4096);
```

And can now write to the shared memory (after mapping it into its own address space with `mmap`):

```c
sprintf(shared_memory, "Writing to shared memory");
```

**IPC POSIX Producer** (full example):

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <sys/shm.h>
#include <sys/stat.h>

int main()
{
    /* the size (in bytes) of shared memory object */
    const int SIZE = 4096;
    /* name of the shared memory object */
    const char *name = "OS";
    /* strings written to shared memory */
    const char *message_0 = "Hello";
    const char *message_1 = "World!";

    /* shared memory file descriptor */
    int shm_fd;
    /* pointer to shared memory object */
    void *ptr;

    /* create the shared memory object */
    shm_fd = shm_open(name, O_CREAT | O_RDWR, 0666);

    /* configure the size of the shared memory object */
    ftruncate(shm_fd, SIZE);

    /* memory map the shared memory object */
    ptr = mmap(0, SIZE, PROT_WRITE, MAP_SHARED, shm_fd, 0);

    /* write to the shared memory object */
    sprintf(ptr, "%s", message_0);
    ptr += strlen(message_0);
    sprintf(ptr, "%s", message_1);
    ptr += strlen(message_1);

    return 0;
}
```

**IPC POSIX Consumer** (full example):

```c
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <sys/shm.h>
#include <sys/stat.h>

int main()
{
    /* the size (in bytes) of shared memory object */
    const int SIZE = 4096;
    /* name of the shared memory object */
    const char *name = "OS";
    /* shared memory file descriptor */
    int shm_fd;
    /* pointer to shared memory object */
    void *ptr;

    /* open the shared memory object */
    shm_fd = shm_open(name, O_RDONLY, 0666);

    /* memory map the shared memory object */
    ptr = mmap(0, SIZE, PROT_READ, MAP_SHARED, shm_fd, 0);

    /* read from the shared memory object */
    printf("%s", (char *)ptr);

    /* remove the shared memory object */
    shm_unlink(name);

    return 0;
}
```

> **Context:** Notice the consumer calls `shm_unlink(name)` to remove/clean up the shared memory object once done — unlike ordinary process memory, a POSIX shared memory segment persists independently of any single process (it's more like a small named file living in memory) until explicitly unlinked, so cleanup is the responsibility of the programmer, not automatic when a process exits.

### Mach

Mach's IPC is **message-based** — even system calls themselves are implemented as messages.

- Each task (Mach's term roughly equivalent to a process) gets **two mailboxes** at creation: **Kernel** and **Notify**.
- Only **three** system calls are needed for message transfer: `msg_send()`, `msg_receive()`, `msg_rpc()`.
- Mailboxes needed for communication are created via `port_allocate()`.
- Send and receive are flexible — for example, there are four options available if a mailbox is full:
    - Wait indefinitely
    - Wait at most _n_ milliseconds
    - Return immediately (don't wait)
    - Temporarily cache a message

### Windows

Windows is message-passing centric via the **Advanced Local Procedure Call (LPC)** facility.

- Only works between processes **on the same system** (it is explicitly _local_, unlike RPC, described below, which works across a network).
- Uses **ports** (analogous to mailboxes) to establish and maintain communication channels.

**Communication works as follows:**

1. The client opens a handle to the subsystem's **connection port** object.
2. The client sends a connection request.
3. The server creates two private **communication ports** and returns the handle to one of them to the client.
4. The client and server use their corresponding port handle to send messages or callbacks and to listen for replies.

### Local Procedure Calls in Windows (Diagram)

- The **client** sends a **connection request** to the **connection port**, which returns a **handle**.
- This yields a **client communication port** (handle returned to the client) and a **server communication port** (handle returned to the server) — these two ports are linked to each other.
- For larger data transfers (more than a small threshold), a **shared section object** (≤ 256 bytes in this example) can also be used between client and server directly, avoiding the overhead of passing large messages purely through the ports.

## Communications in Client-Server Systems

Several mechanisms exist for client-server communication:

- **Sockets**
- **Remote Procedure Calls (RPC)**
- **Pipes**
- **Remote Method Invocation (RMI)** (Java-specific)

### Sockets

A **socket** is defined as an **endpoint for communication** — a concatenation of an **IP address** and a **port**, where the port is a number included at the start of a message packet to differentiate network services running on the same host.

- The socket `161.25.19.8:1625` refers to port `1625` on host `161.25.19.8`.
- Communication consists of a connection between a **pair** of sockets (one on each communicating machine/process).
- All ports below **1024** are **well known**, reserved for standard services (e.g., port 80 for HTTP, port 22 for SSH).
- The special IP address **127.0.0.1** (**loopback**) refers to the system on which the process itself is running — useful for a process to communicate with another process on the same machine using networking APIs.

### Socket Communication

Example: a client on host X (`146.86.5.20`) opens a socket `146.86.5.20:1625`, which connects across the network to a web server (`161.25.19.8`) listening on socket `161.25.19.8:80` (the well-known HTTP port). The pairing of these two sockets defines the specific communication channel between the client and the server.

### Sockets in Java

Java provides three types of sockets:

- **Connection-oriented (TCP)** — reliable, ordered delivery; a persistent connection is established before data is exchanged.
- **Connectionless (UDP)** — no persistent connection; faster but not guaranteed to arrive or arrive in order.
- **`MulticastSocket`** class — allows data to be sent to multiple recipients at once.

Example "Date" server (TCP), which listens for connections and, whenever a client connects, sends back the current date/time and then closes that connection:

```java
import java.net.*;
import java.io.*;

public class DateServer
{
    public static void main(String[] args) {
        try {
            ServerSocket sock = new ServerSocket(6013);

            /* now listen for connections */
            while (true) {
                Socket client = sock.accept();

                PrintWriter pout = new
                    PrintWriter(client.getOutputStream(), true);

                /* write the Date to the socket */
                pout.println(new java.util.Date().toString());

                /* close the socket and resume */
                /* listening for connections */
                client.close();
            }
        }
        catch (IOException ioe) {
            System.err.println(ioe);
        }
    }
}
```

### Remote Procedure Calls (RPC)

**RPC** abstracts procedure calls between processes on **networked** systems, letting a program call a function that actually executes on a remote machine as if it were a normal local function call. Like sockets, RPC again uses ports for service differentiation.

- **Stubs** — a client-side proxy standing in for the actual procedure that really lives on the server.
- The client-side stub locates the server and **marshals** the parameters (packages them into a transmittable format).
- The server-side stub receives this message, unpacks (**unmarshals**) the marshalled parameters, and performs the actual procedure on the server, then sends the result back the same way.
- On Windows, stub code is compiled from a specification written in the **Microsoft Interface Definition Language (MIDL)**.

Data representation across different machine architectures is handled via **External Data Representation (XDL)** format, to account for differences such as **big-endian** vs. **little-endian** byte ordering between different hardware.

**Remote communication has more failure scenarios than local communication** (e.g., network dropouts, server crashes mid-call) — because of this, RPC systems generally aim for messages to be delivered **exactly once**, rather than merely **at most once** (i.e., they try to guard against both message loss _and_ duplicate execution, which is much harder over an unreliable network than in local communication).

The OS typically provides a **rendezvous** (or **matchmaker**) service to connect client and server initially, since the client doesn't inherently know which port the server's desired procedure is listening on.

### Execution of RPC

The full sequence for a client calling remote procedure X:

1. The user calls the **kernel** to send an RPC message to procedure X.
2. The kernel sends a message to the **matchmaker** to find the port number for procedure X.
3. The **matchmaker** receives the message, looks up the answer, and replies to the client with **port P**.
4. The kernel places port P in the user's RPC message.
5. The kernel sends the RPC to port P, where a **daemon** listening on port P receives the message.
6. The daemon processes the request and sends output back.
7. The kernel receives the reply and passes it back to the user.

> **Context:** This matchmaker/rendezvous step is analogous conceptually to DNS resolution before a normal network connection — the client doesn't know in advance exactly where to find the service, so a well-known intermediary (the matchmaker) helps it discover the correct destination port before the "real" communication begins.

### Pipes

A **pipe** acts as a conduit allowing two processes to communicate. Several design questions arise for any pipe implementation:

- Is communication unidirectional or bidirectional?
- In the case of two-way communication, is it half- or full-duplex? (Half-duplex: data flows one direction at a time; full-duplex: data flows both directions simultaneously.)
- Must there exist a relationship (i.e., parent-child) between the communicating processes?
- Can the pipes be used over a network?

Two main categories:

- **Ordinary pipes** — cannot be accessed from outside the process that created them. Typically, a parent process creates a pipe and uses it to communicate with a child process that it created.
- **Named pipes** — can be accessed without requiring a parent-child relationship.

### Ordinary Pipes

Ordinary pipes allow communication in a standard producer-consumer style:

- The producer writes to one end (the **write-end** of the pipe).
- The consumer reads from the other end (the **read-end** of the pipe).
- Ordinary pipes are therefore **unidirectional** (data flows in one direction only).
- They require a **parent-child relationship** between the communicating processes (because the pipe's file descriptors must be inherited through the `fork()` mechanism — there's no external name by which an unrelated process could find the pipe).

In the underlying implementation, both parent and child inherit file descriptor pairs `fd[0]` (read end) and `fd[1]` (write end) referring to the same underlying pipe; typically each side closes the end it doesn't need (e.g., the parent closes its read end if it's only writing, and vice versa for the child).

Windows calls these **anonymous pipes**.

### Named Pipes

Named pipes are more powerful than ordinary pipes:

- Communication is **bidirectional**.
- **No parent-child relationship** is necessary between the communicating processes.
- **Several processes** can use the same named pipe for communication (not limited to just two).
- Provided on both **UNIX** and **Windows** systems.

> **Context:** Because a named pipe has an actual name (often appearing as a special file in the filesystem on UNIX, e.g., created via `mkfifo`), any process on the system that knows the name can open and use it, which is precisely what removes the parent-child restriction that ordinary pipes have. This makes named pipes closer in spirit to the indirect/mailbox communication model discussed earlier, just implemented as a filesystem object rather than an OS-managed mailbox.
