## What is an Operating System?

An operating system (OS) is the software layer that manages a computer's hardware and provides a platform on which applications can run. Without an OS, every application would need to know how to talk directly to hardware (disks, memory chips, the CPU, printers, etc.), which would make software both harder to write and unsafe to run alongside other programs. The OS exists as an abstraction layer so applications can make simple requests ("read this file," "draw this pixel") without worrying about the underlying hardware details.

The OS controls things such as:

- The screen and keyboard (input/output)
- Files (creating, reading, writing, organizing)
- Memory (RAM) — deciding what data lives where
- The CPU — deciding which program gets to run and when
- Devices — communicating with printers, USB drives, cameras, etc.
- Security — controlling what users and programs are allowed to do

### Components of a Computer System

A computer system can be thought of as a stack of layers:

1. **Computer hardware** — the physical CPU, memory, and I/O devices at the bottom.
2. **Operating system** — sits directly on top of the hardware and controls it.
3. **System and application programs** — compilers, assemblers, text editors, database systems, etc., which run on top of the OS.
4. **Users** — people interacting with the system through these programs.

Each user interacts with application/system programs, which in turn rely on the OS to actually access hardware resources. This layering is what lets multiple users and multiple programs share one machine safely — the OS acts as the "referee" in the middle.

> **Context:** This is often called a layered or hierarchical view of a computer system. It matters because it shows _why_ the OS is necessary: application programs are written against the OS's interface (system calls), not against raw hardware, so the same program can run on very different hardware as long as the OS provides a compatible interface underneath it.

## What Operating Systems Do

### CPU / Program Management

The OS manages programs that are running. If you open Chrome, Word, and Spotify at the same time, the OS decides how the CPU's time is shared among them — a single CPU core can only execute one instruction stream at a time, so the OS rapidly switches between programs to create the illusion that they're all running simultaneously. This is the basis of **multitasking** (discussed further below).

### File Management

The OS organizes and manages files and folders. It keeps track of where data physically lives on a disk and presents it to the user/programs as a simple folder and file hierarchy.

**Example:** When you save `assignment.pdf` in your Documents folder, the OS manages where and how that file is actually stored on disk (which sectors/blocks it occupies), while presenting you with a simple, human-readable file path.

### Device Management

The OS communicates with hardware devices on behalf of programs, so that individual applications don't need built-in drivers for every possible printer, mouse, or graphics card.

**Example:** When you print a document, the OS communicates with the printer and sends it the information (data + formatting instructions) it needs, using a device-specific driver so the application itself doesn't need to know the printer's technical details.

### Other Responsibilities

- **Device Management** (as above)
- **Security** — controlling access to resources, isolating processes from one another, and authenticating users.

### Application Programs

Application programs define the ways in which system resources (CPU, memory, I/O) are used to solve the actual computing problems of the users. In other words, the OS provides and manages the resources, but it's the application programs (word processors, browsers, games) that use those resources to do something useful for the end user.

## Computer System Organization

### Computer-System Operation

A typical computer system consists of:

- One or more **CPUs**
- Several **device controllers** (e.g., disk controller, USB controller, graphics adapter)

These all connect through a **common bus**, which provides access to **shared memory**.

Example hardware layout:

- **CPU** ↔ bus
- **Disk controller** ↔ disks ↔ bus
- **USB controller** ↔ mouse, keyboard, printer ↔ bus
- **Graphics adapter** ↔ monitor ↔ bus
- All of the above connect to shared **memory** via the bus

The CPU and all the devices can execute **concurrently**, and they compete with each other for memory access cycles on the shared bus. This competition is one reason memory access speed and bus bandwidth are critical bottlenecks in system performance.

### Computer System Operation (Details)

- I/O devices and the CPU can execute concurrently — e.g., a disk can be reading data while the CPU works on something else entirely.
- Each device controller is in charge of a particular device type (e.g., the disk controller only manages disks).
- Each device controller has a **local buffer** — a small amount of memory used to temporarily hold data being transferred.
- The CPU moves data to/from main memory from/to these local buffers.
- I/O itself (the actual physical transfer) happens between the device and the local buffer of its controller — the CPU is not directly involved in that low-level transfer.
- Once its operation is finished, the device controller informs the CPU by causing an **interrupt**.

> **Context:** This separation (device ↔ local buffer ↔ CPU ↔ main memory) is what allows slow devices (like a printer or disk) to operate without freezing the entire computer — the CPU can go do other work and simply gets notified via an interrupt when the device is done, rather than sitting and waiting (a wasteful approach called "polling" or "busy-waiting").

### Interrupt Timeline

An interrupt is a signal that pauses the CPU's normal execution so it can immediately handle an event that just occurred (such as a device finishing a task).

The typical sequence looks like this:

1. The user process is executing normally on the CPU.
2. An **I/O request** is issued (e.g., "read this file from disk").
3. The CPU continues executing the user process while the I/O device is **transferring** data in the background.
4. When the **transfer is done**, the device raises an **interrupt**.
5. The CPU briefly pauses the user process to run **I/O interrupt processing** (a small piece of code called an interrupt handler).
6. Once the interrupt is handled, the CPU resumes the user process where it left off.

This cycle (request → transfer → interrupt → resume) repeats every time a program needs I/O, and it's what allows the CPU to stay productive instead of idling while waiting on slow devices like disks or printers.

## Operating System Operations

Modern operating systems are **interrupt driven** — almost everything that happens in the OS is triggered by some kind of interrupt or exception, rather than the OS constantly polling for work. There are two broad categories:

**Hardware interrupts:**

- Caused by one of the devices (e.g., a disk finishing a read, a key being pressed, a network packet arriving).

**Software interrupts (also called traps or exceptions):**

- **Software error** — e.g., division by zero, or an attempt to access invalid memory. The CPU detects the error condition and traps into the OS.
- **Request for OS** — a program deliberately asks the OS to do something on its behalf, called a **system call** (e.g., "open this file," "allocate more memory"). This is a controlled, deliberate trap into the OS, as opposed to an error trap.

> **Context:** The professor would likely emphasize that this interrupt-driven design is fundamental to _all_ modern OS behavior — the OS is essentially dormant, waiting for interrupts, and only executes when one of these three things (device interrupt, error trap, or system call) occurs. This is more efficient than an OS that must constantly check ("poll") whether something needs attention.

## Operating System Structure

**Multitasking** (also called multiprogramming/time-sharing) is a logical extension of running one program at a time: the CPU switches between jobs (programs) so frequently that users can interact with each job while it is running, creating **interactive computing**.

Key related concepts:

- **Response time** should be less than 1 second for the system to feel interactive/responsive to a human user.
- If several jobs are ready to run at the same time, the OS needs a policy to decide which runs next — this is **CPU scheduling**.
- If processes (running programs) don't fit entirely in physical memory, **swapping** moves parts of them in and out of memory as needed to keep the system running.
- **Virtual memory** allows execution of processes that are not completely loaded into physical memory at once — a process can appear to have access to more memory than physically exists.
    - A file (on disk) can act as virtual memory — this is sometimes called a "swap file" or "page file," and it's how the OS extends usable memory beyond physical RAM by temporarily storing inactive memory pages on disk.

> **Context:** Multitasking and virtual memory are two of the most important ideas in OS design because they're why you can run dozens of browser tabs, a music player, and a word processor simultaneously on a machine that doesn't have enough physical RAM to hold everything at once, without programs crashing or needing to know about each other.

## Process Management

A **process** is a program in execution — it is a unit of work within the system. The distinction between a program and a process is important:

- A **program** is a _passive_ entity — it's just a file sitting on disk (e.g., an executable), a set of instructions.
- A **process** is _active_ — it's a program that has been loaded into memory and is actually running (or waiting to run), with its own current state (registers, memory, program counter, etc.).

A process needs **resources** to execute, including:

- **CPU** time
- **Memory**
- **I/O** access
- **Files**
- **Initial data**

> **Context:** A useful analogy: a program is like a recipe (static instructions), while a process is like the actual act of cooking that recipe (an active instance, using ingredients/resources, that can be paused and resumed). You can run the _same_ program multiple times, creating multiple separate processes (e.g., opening two Chrome windows creates multiple Chrome-related processes), each with its own resources and state.

## List of Common Operating Systems

### 1. Desktop and Laptop Operating Systems

- **Microsoft Windows** — Windows 10, Windows 11
- **Apple macOS** — used on Mac computers
- **Linux** — Ubuntu, Fedora, Debian, Red Hat
- **ChromeOS** — used on Chromebooks

### 2. Mobile Operating Systems

- **Android** — Google/Samsung and many other phones
- **iOS** — Apple iPhone
- **iPadOS** — Apple iPad

### 3. Server Operating Systems

- **Windows Server**
- **Linux Server** — Ubuntu Server, Red Hat Enterprise Linux, Debian
- **Unix**
- **FreeBSD**

### 4. Real-Time Operating Systems (RTOS)

Used where fast and predictable responses are important (e.g., industrial control, automotive systems, medical devices) — correctness in these systems depends not just on getting the right answer, but on getting it within a strict, guaranteed time limit.

- FreeRTOS
- VxWorks
- QNX
- Zephyr
- RTEMS

### 5. Embedded Operating Systems

Used in devices such as cars, routers, appliances, and IoT devices — typically lightweight OSes designed to run on hardware with limited memory/processing power, often dedicated to a single or small set of tasks.

- Embedded Linux
- QNX
- FreeRTOS
- Zephyr
- ThreadX

> **Context:** Note that some OSes (QNX, FreeRTOS, Zephyr) appear in both the RTOS and Embedded categories — that's because embedded systems (like a car's engine control unit) very often _require_ real-time guarantees, so the two categories overlap heavily in practice rather than being fully distinct.
