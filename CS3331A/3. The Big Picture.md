## Decision Problems

A **decision problem** is a problem whose answer is always yes/no (True/False). A **decision procedure** is an algorithm that answers a decision problem.

Example: _Given an integer $n$, does $n$ have a pair of consecutive integers as factors?_

The course's central focus is one particular decision problem template, the **language recognition problem**:

> Given a language $L$ and a string $w$, is $w \in L$?

This is the "focus" problem because — as this chapter argues — essentially _any_ computational problem can be recast into this form.

## The Power of Encoding

**Core idea: everything is a string.** Any object (a number, a graph, a program, a protein) can be encoded as a string, and any question about that object can be recast as "is this encoded string in a particular language?"

Notation: $\langle X \rangle$ denotes the string encoding of object $X$; $\langle X, Y \rangle$ denotes the encoding of the pair $(X, Y)$.

This reframing is what makes the language-recognition framework so general — it isn't restricted to "obviously string-like" problems (parsing, text search); it can capture arithmetic, graph theory, biology, and program verification questions too.

### Worked Examples of Encoding

**Pattern matching**: Given a search string $w$ and a document $d$, should a search engine return $d$ for query $w$? $$L = {\langle w, d\rangle : d \text{ is a candidate match for the query } w}$$

**The halting problem** (does a program always halt?): Given a program $p$, is $p$ guaranteed to halt on all inputs? $$HP_{ALL} = {p : p \text{ halts on all inputs}}$$ (This is a preview of a famously _undecidable_ language, covered in depth later in the course.)

**Primality testing**: Given a nonnegative integer $n$, is it prime? Encode each integer as a binary string, then: $$PRIMES = {w : w \text{ is the binary encoding of a prime number}}$$

**Graph connectivity**: Given an undirected graph $G$, is it connected?

- Encode $G$ as $\langle G \rangle$: write $|V|$ in binary, then list edges as binary vertex-pairs, separating all numbers with `/`. E.g. the graph with edges {1-2, 1-4, 2-3, 2-5} and 5 vertices might be encoded as `101/1/10/10/11/1/100/10/101`. $$CONNECTED = {w \in {0,1,/}^* : w \text{ encodes a connected graph as above}}$$

**Protein sequence alignment**: Given a protein fragment $f$ and a full protein $p$, could $f$ be a fragment of $p$? Represent each amino acid as a letter (e.g. `AGHTYWDNR`), then: $$L = {\langle f, p\rangle : f \text{ could be a fragment from } p}$$

This shows the framework applies well outside classical CS — computational biology, search, and networking all reduce to language recognition once you fix an encoding scheme.

## Turning Non-Decision Problems Into Decision Problems

Not every interesting problem is naturally yes/no — e.g., _compute the product of two integers_ or _sort a list_. These can still be recast as decision problems by **transforming computation into verification**: instead of asking the machine to produce the answer, ask it to confirm whether a _proposed_ answer is correct.

**Multiplication as decision**: $$L = {w \text{ of form } \langle int_1\rangle\text{x}\langle int_2\rangle{=}\langle int_3\rangle : int_3 = int_1 * int_2}$$

- `12x9=108` ∈ L
- `12x8=108` ∉ L

**Sorting as decision**: transform "sort this list" into "does this second list represent the sorted version of the first list?" $$L = {w_1 \# w_2 : \exists n \geq 1\ (w_1, w_2 \text{ both encode length-}n \text{ integer lists}, w_2 \text{ has the same elements as } w_1 \text{ and is sorted})}$$

- `1,5,3,9,6#1,3,5,6,9` ∈ L
- `1,5,3,9,6#1,2,3,4,5,6,7` ∉ L (different multiset of elements, and wrong length)

### Why This Recasting Is Legitimate: Equivalence via Reduction

The traditional (compute-the-answer) version of a problem and its language-recognition version are considered **equivalent**, meaning each can be **reduced to** the other: if you have a machine that solves one, you can build a machine for the other using just that machine plus operations no more powerful than it.

- Given a **multiplication machine**, you can build the language-recognition machine: compute $int_1 * int_2$ and check whether it equals $int_3$.
- Given the **language-recognition machine** (for the decision version), you can build a multiplication machine: for each candidate product value, ask the decision machine whether $\langle int_1\rangle\text{x}\langle int_2\rangle{=}\langle candidate\rangle$ holds, searching until you find the one it accepts.

This equivalence is what justifies studying decision problems as a stand-in for computation problems generally — nothing is lost in the translation, provided the "search for the answer" direction is itself effectively computable (e.g., bounded, or with a known search strategy).

## Languages and Machines: The Hierarchy

The course organizes languages into nested classes, each associated with a class of abstract machine that can recognize exactly that class of languages:

|Language class|Recognizing machine|
|---|---|
|Regular languages|Finite State Machines (FSMs)|
|Context-Free Languages|Pushdown Automata (PDAs)|
|Decidable (D) Languages|Turing Machines (that always halt)|
|Semi-Decidable (SD) Languages|Turing Machines (may run forever on rejects)|

These nest: Regular ⊂ Context-Free ⊂ Decidable ⊂ Semi-Decidable, and each outer class corresponds to strictly more computational power than the one inside it.

### Finite State Machines (FSMs)

An FSM has a finite set of states and transitions on input symbols, with no auxiliary memory beyond "which state am I in."

- An FSM can accept $a^*b^*$ (any number of a's followed by any number of b's) — easy, since it just needs to remember "have I seen a b yet."
- An FSM **cannot** accept $A^nB^n = {a^nb^n : n \geq 0}$ (equal numbers of a's then b's) — because that requires counting an unbounded number of a's and comparing to the number of b's, and an FSM has no memory to store an unbounded count. (This is a preview of the **pumping lemma** style argument used later to _prove_ certain languages aren't regular.)

### Pushdown Automata (PDAs)

A PDA is an FSM plus a **stack** — unbounded memory, but only accessible in last-in-first-out order.

- A PDA **can** accept $A^nB^n$: push a marker for each `a`, then pop one for each `b`, accepting if the stack empties exactly when the input ends. Example trace on `aaabb`: push on each of the 3 a's, then pop on each of the 2 b's — leaving a nonempty stack (1 marker unpopped), so `aaabb` is correctly rejected (it doesn't have equal a's and b's).
- The language `Bal` (balanced parentheses) is the classic PDA example — the stack naturally tracks "how many opens are still unmatched."
- A PDA **cannot** accept $A^nB^nC^n = {a^nb^nc^n : n \geq 0}$ — matching two independent counts (a's-to-b's AND b's-to-c's) simultaneously exceeds what a single stack can track, since by the time you're comparing c's to b's, the information about how many a's there were is already consumed.

### Turing Machines (TMs)

A Turing machine has an unbounded **tape** that can be read _and written_, with a read/write head that can move in both directions — strictly more powerful than a stack.

- A TM **can** accept $A^nB^nC^n$: it can make repeated passes over the tape, crossing off one `a`, one `b`, and one `c` per pass, accepting if everything is crossed off evenly.
- A TM can also decide problems like: _does Java program $p$ halt on input 0?_ — by directly simulating $p$ running on input 0. (Note: this only decides _one specific input_; deciding whether $p$ halts on _all_ inputs, i.e. $HP_{ALL}$ from earlier, is a fundamentally different — and undecidable — question, covered later.)

### Rule of Least Power

> "Use the least powerful language [or machine] suitable for the given problem."

This is a recurring design principle: if a regular language / FSM suffices, don't reach for a context-free grammar or a full Turing machine. Weaker formalisms are typically easier to reason about, more efficient to implement, and easier to prove properties about (e.g., regular expressions in text editors, XML schemas vs. full programming languages for config files).

## Grammars, Languages, and Machines

Two different but related ways to specify a language:

- A **grammar** _generates_ a language (a set of rewriting rules that produce every string in $L$ and nothing else).
- A **machine** _accepts_ a language (an algorithm/automaton that, given a string, determines whether it's in $L$).

For each level of the language hierarchy above, there's a matching grammar formalism (e.g., regular expressions/grammars ↔ FSMs; context-free grammars ↔ PDAs) — generation and acceptance are two sides of the same coin, a theme developed in later chapters.
